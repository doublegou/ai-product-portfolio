# 内容生产 Agent 与 Skill 工作流

**面向独立科技内容创作者，将视频、口播稿、产品资料与热点线索，转成可编辑、可检查的内容素材。**

这是一个在个人真实创作中使用、持续迭代的 AI 产品项目。四个模块覆盖选题研究、视频改编、口播配套素材和产品内容；使用入口是对话中的 Skill 与本地程序。项目关注一次创作任务如何从输入走到交付，以及需求变化、事实错误和部分失败如何处理。

[Quick Start](docs/quick-start.md) · [产品决策与验证设计](docs/case-study.md) · [评测数据](evaluation/2026-10-17-product-audit/README.md) · [源代码](src/)

## 产品机会：让反复创作可以接续

创作任务通常从已有材料开始：看到一条值得改编的视频、写完一期口播稿，或需要介绍自己的产品。一次对话能生成初稿，但后续还要调整结构、同步素材、核查事实。**重复说明要求和追踪修改，成为生成之后的主要工作。**

真实任务形成了三个设计约束：

- **允许改变要求。** 卡片从八张改六张，仍要保留完整解释；需要在出图前改结构。
- **承接已经完成的工作。** 已有实机演示时，只生成文案和封面；“整套生成”不能成为必经步骤。
- **交付状态要可信。** 模型给出高分仍可能有事实问题，发布准备失败也不应该掩盖已经保存的草稿。

因此，产品以“本次约定的素材能否取用”为完成标准，保留中间材料、修改入口和失败原因。当前需求证据来自个人使用；是否适用于更多创作者，仍需要后续验证。

## 产品架构与使用路径

![四个模块的输入、执行、产物与人工控制点](docs/diagrams/architecture.svg)

四个模块可以独立使用，通过明确的文件交接；图中没有统一自动调度。内容理解、创作和语义审稿由模型完成，采集、文件规格、状态与停止条件由程序控制。

| 用户从哪里开始 | 正常使用过程 | 完成时检查什么 |
| --- | --- | --- |
| **content-workflow** · 一条视频 | 提交链接 → 查看分析 → 调整卡片规划 → 确认出图 → 取用正文与图片 | 引用可回查；卡片可独立理解；图片符合约定规格 |
| **script-workflow** · 一期口播稿 | 选择所需素材 → 生成 → 播放或编辑 → 反馈修改 → 核对本期文件 | 演示跟随口播；标题和封面承诺一致；使用同一版稿件 |
| **content-agent** · 产品与账号资料 | 指定产品或主题 → 研究写作 → 有限审改 → 保存 → 逐项事实复核 | 结构完整；主张有依据；草稿与发布状态分别确认 |
| **daily-trend-radar** · 研究方向 | 选择来源 → 采集报告 → 回查原文 → 筛选角度 → 决定是否继续创作 | 来源和时间可解释；选题与受众相关；缺失证据已标明 |

## 四个真实案例

### 01 · content-workflow：把视频改编成独立可读的图文

**输入与目标。** 一条讨论 AI 文献综述的视频，改编为中文正文和系列卡片。用户在规划阶段提出：

> “图片八张有点多了，6张吧……除了首页每页内容稍微多一点，就是我只看图片，我也能看懂在说啥。”

摘自[历史对话](demo/content-workflow/2026-08-27-literature-review/conversation-excerpts.json)，省略了风格修改部分，原文可回查。

**设计与修改。** `yt-analysis` 形成共享分析；`note-writer` 写正文，`note-images` 单独规划图片。八页改六页时，将“效率冲击＋综述目的”合并，将“提问反驳＋可信性风险”合并，保留核查与行动建议。确认点放在规划之后，避免把结构问题带到整套成图中。

**正文与卡片是两份可独立使用的产物。** 正文保留连续论证，卡片把观点转成对照和步骤。下面先给出[实际正文](demo/content-workflow/2026-08-27-literature-review/result/post.md)的一段，再看对应图片如何完成解释：

> 拿到AI综述后，先查引用。论文真的存在吗？原文支持这句话吗？它和你的问题有关吗？引用报告能帮你缩小范围，但不能替你做判断。

### 02 · script-workflow：同一期口播稿的完整素材交付

**输入主张 → 三种表达。** [修订口播稿](demo/script-workflow/2026-09-26-agentic-video/input-script-revised.md)的核心是“AI 开始自己决定，它需要什么 Context”。演示用两次 Processing Call 解释过程；发布标题改为“AI看长视频，开始会自己找答案了”；封面再压缩成“AI自己翻视频”，副标题“沿着时间轴找答案”。每一步都调整表达形式，保留同一内容承诺。

### 03 · content-agent：用事实复核检验“模型已通过”

**输入与目标。** 用 BirdTracker 产品资料、账号表达规则和平台规范，生成面向观鸟新手的候选稿。稿件需要解释具体使用方式，避免编造亲历或扩大功能承诺。

**设计与修改。** 程序组织研究、写作和最多五轮审改；本地规则先筛查，模型继续评价并提供修改意见。历史稿第二轮达到 8.6 分后保存，但逐项复核九项主张，仍有四项需要删除或调整。

| 历史已通过稿件 | 复核后的表达 | 产品判断 |
| --- | --- | --- |
| “我用手机记下了第一次观鸟日记” | “把散步时看到的鸟，留在自己的观察记录里” | 没有亲历依据时，用使用场景表达 |
| “选一个鸟多的地方去” | “热点提供地点线索，实际鸟况仍需现场观察。” | 地点线索不构成结果保证 |
| “每拍下一只鸟，它就会出现在『荣誉』页面里” | 删除该承诺，按资料介绍最近记录 | 功能关联必须有产品依据 |

**修订后的候选内容：**

> **把散步时看到的鸟，留在自己的观察记录里**
>
> 散步时，你会不会停下来多看一眼路边的鸟？想认识它，也想留下这次观察，可以从查资料、找地点和做记录开始。BirdTracker 把图鉴、热点地图和相机记录放在一起，为刚开始观鸟的人提供一个入口。

开头直接交代读者场景和可做的事情；完整稿继续说明查图鉴、找地点、保存与回看记录。审校说明留在复核记录中，不混入面向读者的正文。

**交付结果。** 历史草稿与审改日志、九项主张核查、修订候选稿均可查看。另修复“草稿已保存，发布异常却令保存计数为零”的问题；回归验证失败时仍保留部分成果。修订稿尚未记录最终采用。

这次历史运行有完整用量：**6 次模型调用、102,306 Token、整次运行 241.341 秒**。它证明了生成投入，也暴露出评分与事实之间的差距，不能作为已发布内容的成功成本。

### 04 · daily-trend-radar：把榜单线索变成有依据的选题

**输入与目标。** 为 AI 与科技内容寻找下一期主题，采集 GitHub、Hacker News、V2EX 各五条。交付应说明“为什么值得讲、已有何种证据、还需验证什么”。

**设计与修改。** Node 工具采集并统一字段，Agent 回查原文、形成角度，用户决定是否进入制作。2026-10-16 直接连接失败后通过已有代理取得报告；失败报告保留，发布时间缺失的条目只表述为当前在榜。

| 报告中的来源条目 → 候选角度 | 对目标读者的价值 | 制作决策 |
| --- | --- | --- |
| `claude-plugins-official` → 装了 Skill，为什么还需要插件目录？ | 用已有 Skill 实践解释能力与分发配置的关系 | 优先研究，可结合现有材料举例 |
| `scientific-agent-skills` → 科研 Skill 能替代科研判断吗？ | 延续文献综述案例，讨论结论核查 | 适合图文，具体效果需任务验证 |
| `context-mode` → 工具输出太多，如何控制上下文？ | 解释长任务的信息筛选与回查 | 安装与对照尚未完成，暂缓教程 |

**交付结果。** 15 条来源记录和三个候选角度；其中十条无发布时间，三个候选均来自 GitHub。2026-10-17 又连续实采三次，各取得三源 15 条。采集可重复与选题会被采用，是两个不同的验证问题。

## 关键技术方案

| 环节 | 当前实现 | 对产品体验的影响 |
| --- | --- | --- |
| 视频内容获取 | `yt-dlp` 按语言选择人工／自动字幕；没有可用轨道时，经确认下载音频，由 **Whisper base 在 CPU 本地转写**；FFmpeg 处理音频 | 优先利用已有字幕；无字幕仍有继续路径。转写会增加等待，时间戳与识别内容需要复核 |
| 卡片与封面生成 | 当前 Skill 使用宿主 **`image_gen`**；卡片先生成封面作为风格参考，三比例封面同时保留原始人像与主设计参考 | 将文字、身份与系列风格作为输入约束；只修订失败项，实际比例和中文仍须验收 |
| 图片 API 实现 | 仓库另保留 **`gpt-image-2` API 生成器**，支持 chat / images 端点及回退、瞬态重试和比例重生 | 它是可查看的接口实现，当前 Skill 未接入为默认通道；历史案例的内置出图记录未提供底层模型版本 |
| 结构化内容生成 | OpenAI 兼容接口、JSON 解析与 Pydantic 校验；格式纠正和内容审改分别限次；SDK 请求失败时有 HTTP / curl 备用路径 | 分开处理“连接失败、格式错误、内容不合格”，避免同一种重试处理全部问题 |
| 多源采集 | 请求默认 10 秒超时、最多额外重试两次，**指数退避 300 / 600 ms**；跨平台并发、同平台串行；逐源保留状态 | 控制等待与同平台请求压力；部分失败仍交付可用来源，全失败也保留诊断报告 |

这里的 **fallback（失败后换路径）**、**backoff（重试前退避等待）** 和 **backend（实际生成后端）** 是不同设计。完整触发条件、模型配置、实现入口与限制见[技术架构详解](docs/architecture.md#4-字幕获取与-whisper-降级)。

## 质量、成本与下一步投入

本轮不把四类任务合成一个成功率。按具体产品问题评测，保留分母和失败样本：

| 评测问题 | 当前证据 | 对下一步的影响 |
| --- | --- | --- |
| 事实规则能否识别风险表达？ | **12 条构造边界样本，6 条符合预期，3 条漏报、3 条误报** | 先处理主张依据和否定语义，避免用更高总分掩盖事实问题 |
| 研究运行成功是否取得素材？ | 历史 10 次策略采集均标记 success；9 次有汇总，其中 **6 次创作者与笔记均为零** | 将程序成功与研究素材可用分开，空结果应显式进入降级 |
| 多轮审改投入是否值得？ | 另一条历史运行五轮仍未通过，已知用量 **至少 121,611 Token** | 先定位资料缺口和上下文冗余，再比较一次生成与有限审改 |
| 雷达能否重复取得报告？ | 同一代理环境连续三次各取得 15 条，耗时 **1.746 / 0.960 / 0.629 秒** | 进入跨日来源监测；选题采纳另测，不以抓取速度代替价值 |

边界样本有意覆盖易出错表达，由当前助手设定期望，不代表生产分布或模型准确率。历史日志共 189 个事件；无起始事件的片段不纳入完整运行分母。详细输入、原始结果、统计代码及假设价格下的费用分析见[产品评测](evaluation/2026-10-17-product-audit/README.md)。

下一步优先解决事实错误、空结果和版本传递，再测量**约定交付完成率、人工修正时间、单个合格交付成本**。统一调度放在更后面：先确认雷达选题确实会被用于创作。具体对照方案和改变优先级的条件见[产品决策](docs/case-study.md)。
