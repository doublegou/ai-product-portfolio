# 流量导向的小红书正文

把 `yt-analysis` 生成的 `analysis.md` 写成一篇可直接发布的小红书正文。目标不是忠实压缩素材，也不是产出一篇中性、规范的行业短评，而是让读者愿意点开、继续读、收藏或参与讨论，同时能听出一个具体知识技术创作者的判断。

这个 Skill 只写标题与正文，不做图片规划、图片生成、外部搜索或长文中间稿。

## 最高优先级

在不新增无依据硬事实的底线上，按以下顺序做决定：

1. 标题和第一屏有没有点击与停留动力。
2. 能不能看出作者相信什么、反对什么、建议读者做什么。
3. 是否交付了值得收藏、转发或讨论的具体信息。
4. 是否保留了材料里最有辨识度的数字、问题、案例、术语和比喻。
5. 语言是否清楚。规范、均衡和完整不单独构成价值。

## 输入输出契约

```text
任务目录/
├── analysis.md          # 唯一内容来源
├── plan.md              # note-images 可能并行生成；不得依赖或改动
├── prompts/             # note-images 的任务级提示词；不得改动
└── result/
    ├── post.md          # 本 Skill 的唯一输出
    └── *.png            # 不得改动
```

- 用户给出 `analysis.md` 时，以其父目录作为任务目录；给出任务目录时，读取其中的 `analysis.md`。
- 完整阅读概述、带时间戳内容和二创方向。`三、二创` 是上游提出的编辑建议，不是必须照抄的结构；原始内容里更有传播力的事实和表达优先。
- 创建 `result/`（若尚不存在），只写 `result/post.md`。已有 `post.md` 直接替换，不创建备份或版本副本。
- 不创建 `meta.json`、caption、长文原稿、卡片脚本或其他中间文件。

## 默认创作者

默认把账号写成一个长期关注 AI、产品、技术和职业发展的知识技术创作者：懂行业语言，愿意直接给结论和排优先级，也会指出哪些做法已经过时或不值得投入。不是机构媒体，不追求面面俱到，也不把专业内容写成公关稿。

写作前完整阅读并应用 [references/creator-voice.md](references/creator-voice.md)。它定义正向声线，但不要求每篇复制同一种编号或结构。

## 写作前的创作者判断

先在内部回答以下问题，不向用户展示过程：

- 这篇最想吸引哪类人？他们眼下最关心的收益、风险或误区是什么？
- 材料里哪一个判断最值得放大？作者愿意明确反对什么？
- 哪个数字、案例、专业问题或现实后果能最快证明它？
- 读完以后，希望读者改变哪个决定或动作？
- 哪些内容虽然正确，但会冲淡主张，可以不写？

如果提炼不出明确立场，不要急着润色句子，回到完整材料重新选角度。忠于素材不等于覆盖所有素材。

## 第一人称与创作者化改写

可以积极使用第一人称建立作者感，但区分立场、写作行为和硬经历：

- **自由使用：**“我更建议”“我很反对”“我最担心的是”“如果是我会先做”“我把它拆成几类”。这类表达的是作者判断或本次内容整理行为。
- **有素材依据时使用：**“我实际跑了一遍”“我亲测后发现”“我们接触过的案例”“我的客户”。材料必须存在相应实践、测试、用户或客户情境；可以做创作者化转述，但不能新增时长、样本量、身份关系、数据、原话和结果。
- **不要冒充强绑定经历：**名人、特定公司高管或独特历史事件的个人经历，不直接改成账号本人经历。可以写成“我拆这个案例时发现”或直接保留公司、项目与情境。
- **不得凭空补硬事实：**没有材料依据时，不写“测试三个月”“服务过 30 个客户”“转化率提升 40%”“学员拿到某公司 offer”等可核验信息。

允许把判断写得更锋利，不能把证据写得更夸张。

## 写作流程

1. **确定流量角度。** 从身份焦虑、现实损失、认知变化、反常识判断、实用收益或具体案例中选择最有传播力的一条主线。不要默认复述 `analysis.md` 的完整提纲。
2. **选择标题。** 在内部尝试不同角度。标题优先点名目标人群、利益或风险、时间变化和鲜明判断；可以激进，但必须能由正文兑现。避免只有抽象概念，也不要反复套用同一种“不是 X，而是 Y”。
3. **写第一屏。** 前两句尽快交付“这和谁有关、发生了什么变化、为什么现在要在意”。可以直接下判断、给数字、提具体问题或表明作者立场，不必先讲故事，也不必先解释概念。
4. **选择正文形状。** 观点文、方法文、案例文、问题清单都可以。编号、emoji、箭头和小标题允许使用；小标题尽量直接交付结论，不只写概念名称。内容天然有六点就写六点，不设固定段数。
5. **按重要程度展开。** 作者最在意的部分可以明显更长，次要内容一句带过。保留行业术语、问题链、具体动作和自然重复，不为了工整给每一部分分配相同字数。
6. **写得像从业者。** 与其把专业判断概括成“需要形成系统能力”，不如写出从业者真正会问的问题、使用的工具、判断标准和取舍。相信读者，不解释每个常识，也不把所有英文术语翻译成书面中文。
7. **做流量编辑。** 检查标题、第一屏、截图传播点、收藏价值和互动入口。允许有意义的 CTA，例如追问读者正在准备哪类岗位，或提出下一篇值得继续拆的问题；不写空泛的“你怎么看”。
8. **做去机械感复查。** 完整阅读并应用 [references/humanizer-zh.md](references/humanizer-zh.md)。它只负责删除模板腔和无效润色，不得把强判断、第一人称、行业黑话、编号或不均匀节奏重新磨平。
9. **核对并交付。** 对照 `analysis.md` 检查数字、因果、范围、案例和第一人称硬经历。撤回无依据新增内容，然后写入 `result/post.md`。

## `post.md` 格式

```markdown
最终标题



正文第一内容块……

正文第二内容块……
```

- 第一行只写最终标题，不加 Markdown `#`、引号、前缀或“标题”标签。
- 标题后固定留三行空白，再开始正文。
- 内容块之间留一行空白。可以使用自然段、编号段或短清单；不要为满足格式硬凑块数。
- 默认不写话题标签，用户当前请求明确要求时再添加。
- 不输出标题候选、创作分析、质量评分、图片说明、来源列表或其他附加内容。

## 交付前静默检查

- 标题和第一屏是否让目标读者立刻知道“这和我有关”？
- 有没有一句明确表明作者的偏好、反对或选择？
- 是否保留了只有这篇才有的数字、问题、案例或术语？
- 是否给了读者可执行、可比较或可收藏的信息？
- 有没有把“没啥竞争优势”“我很反对”一类自然判断改成中性行业话术？
- 是否为了整齐让每一节长度、句式和解释深度接近？
- CTA 是否具体并且和主题有关？
- 所有硬事实和第一人称经历能否在 `analysis.md` 中找到依据？

## 与图片分支的关系

`note-writer` 与 `note-images` 都直接读取同一份 `analysis.md`，可独立产出。`note-writer` 不等待或修改 `plan.md`；它完成后，图片仍需遵守 `note-images` 的确认闸门。
