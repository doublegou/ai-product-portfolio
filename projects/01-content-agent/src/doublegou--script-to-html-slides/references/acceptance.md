# 验收方法与技能校准

## 什么可以证明，什么不能

技能 YAML 合法只能证明可解析。HTML 可打开只能证明基础可用。自动检查没有溢出不能证明图示正确、画面漂亮或像参考。把下面三层分别检查，不给一个没有依据的总分或“保证符合”。

### 内容层：对照本次对话中的脚本

在工作上下文中梳理“重要论点 → 对应页/展示节点”，不另存脚本或额外分镜文件。说明性细节可以由口播承担，关键结论、对比、转折和限定不能因压缩而反转或消失。

- 原文中的数字、单位、范围、专有名词是否保持一致？
- “可能、特定条件下、不一定”等限定是否在相关图示或短句中保留？
- 对比图是否错误暗示非黑即白？因果箭头是否把相关性画成因果、把可能画成必然？
- 插图是否表达了这一页的具体关系，而不只是主题相近的装饰？
- 有没有加入脚本没有提供或未经核实的新事实？

发现意思改变属于必修问题，不能用排版好看来抵消。

### 技术层：浏览器实际运行

对于每套演示，检查所有页完整状态；对于分步页，再检查关键中间状态。不能仅查看源代码或一张封面截图。

- 可在 file:// 打开；字体加载完成后再测量和截图。
- 图片、字体、CSS、JS 不请求远程资源、不依赖旁边文件。检查资源引用与实际加载；若环境不能模拟断网，说明仅验证了哪一部分。
- 1280×720 及一个窄屏窗口中，画布保持 16:9，内容位置与相对字号不变化。
- 活动页只有一页，隐藏页不接收点击。检查文本自身溢出和元素超出舞台两种情况；对线条穿字、图形遮挡仍须看截图。
- 完成一次完整的推进、回退、跨页、重播、纯画面切换；重复快速按键后页面仍处于合法节点。首尾页不能进入不存在的页。
- 浏览器没有影响使用的运行错误、缺字方框、缺失图像或未完成的加载。
- 每次生成仅新增一个编号 HTML；修改演示不额外创建版本。用户要求保存在 ppt/script-to-html-slides/ 的技能项目是长期工具，不是每次演示的附加产物。临时检查文件在系统临时目录。

可把确定且重复的检查固化成脚本，但新脚本必须实际运行。布局检测须考虑隐藏元素、变换缩放及 SVG；不要拿未经验证的检测脚本的“通过”当成结果。

### 视觉层：对照本套方向、参考或认可样板

有参考时只比较演示画面；无参考时对照本套设计决策。技术检测通过后仍要检查：

- 是否贯彻本套选定的视觉方向？若选黑板则检查手绘语言；若选编辑或科技方向，则按其字体、图形和空间规则判断，不能拿黑板配色要求所有成品。
- 中文标题和正文是否自然清晰、符合所选气质？中英文混排是否像同一套系统？手写感仅在选择手写方向时检查。
- 标题、内容区、图文间距和边距是否有规律？留白、密度和主次是否服务本页表达，而非机械套同一位置？
- 插图的线条、透视、部件关系是否可信？复杂实物线稿如果画不准，改用解释关系的简图，不用细节堆砌掩盖问题。
- 一眼能否判断重点？是否为了图形或固定版式塞入了不需要的内容？
- 分步显示是否符合讲述顺序？箭头和结论有没有提前泄露后续内容？

不采用“与参考像素相似度达标”作为视觉判断：换成中文、换主题后，正确的画面自然会有不同像素。同系列认可的中文样板可作为后续对齐依据；新系列或用户要求变化时可采用新的设计方向。

## 技能评估案例（合成输入）

这些内容仅用于检查技能，不属于用户脚本，不应自动写入正式 ppt 目录。需要评估时显式使用系统临时目录作为输出目录。以下是测试设计，不是通过记录；实际执行范围见 [实现验证记录](validation.md)。

1. **短提纲与对比**
   - 输入：“这期讲缓存是什么、什么时候有效、什么时候不适用。把已经算过的结果存起来，下次命中缓存就可直接使用；未命中仍要重新计算。”
   - 检查：提纲不超过三个主点；命中/未命中分支明确；不能变成‘缓存总是更快’；无必要时不扩展为复杂系统架构。
2. **中文因果与限定**
   - 输入：“假设每次调用成本从 10 元降到 2 元。更低成本可能带来更多调用，但总支出是否下降，还取决于调用量。这只是一个演示例子。”
   - 检查：10 元、2 元和假设性质保留；可能性不被改成必然；图示能解释单位成本与总支出的区别；不能伪造成真实产品数据。
3. **高密度、中英混排与分步**
   - 输入：“系统依次接收任务、读取文件、调用 API、检查结果。检查失败就回到执行步骤；结果通过后才返回用户。Context Window 是本次可处理信息的范围，不能把它直接等同于长期记忆。”
   - 检查：流程闭环正确，返回用户不出现在检查通过之前；Context Window 不被错误翻译或截断；流程与概念区别在需要时拆页而非缩小字。
4. **修改与输出纪律**
   - 输入：在已生成的测试 HTML 中，把一个短标题替换为明显更长的中文标题，增加一个必要限定，其余内容不改。
   - 检查：只更新指定 HTML；不输出脚本、图片文件或额外版本；长标题不重叠、不截断；原有图示与导航不回归。

真实评估先保存或隔离旧技能基线，再以相同输入生成候选结果。只有实际进行多次或独立生成，才能讨论跨运行稳定性；同一次生成后的自查只是局部证据。报告实际案例、观察到的缺陷和未覆盖范围，不虚构成功率。测试生成的 HTML 和截图留在临时工作区，技能中只保留非敏感、真正有用的回归案例和已认可的通用资源。

## 参考实现及适用边界

以下于 2026-09-23 阅读，仅借鉴设计方法；未安装或运行远端代码。

- [Frontend Slides](https://github.com/zarazhangrui/frontend-slides/blob/main/SKILL.md)：先看真实视觉预览，再沿用所选设计系统；有固定舞台、HTML 架构与动画参考。借鉴视觉探索和套内一致性，不把黑板当成唯一方向，也不强制每次选择三种无关风格。
- [revealjs-skill](https://github.com/ryanbbrown/revealjs-skill)：提供页面骨架、自动溢出检查及逐页截图审查。可借鉴复用与检查方法，不能未经适配就引入外部依赖，破坏单文件输出约定。
- [Anthropic PPTX skill](https://github.com/anthropics/skills/blob/main/skills/pptx/SKILL.md)：区分内容、文件和视觉检查，并强调逐页渲染和修复复查。借鉴验收分层，不采用 PPTX 输出及其要求每页放视觉元素等不适合本参考的规则。
- [Anthropic skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)：用现实输入生成结果、比较基线、结合客观检查与人工视觉反馈迭代。借鉴证据闭环；不把写出测试案例或通过技能文件校验等同于通过效果测试。

## 风格适应性检查

用同一段非敏感内容分别要求黑板、编辑排版和几何科技方向。检查差异是否涉及构图、字体层级、图形处理和节奏，而不只是换背景颜色；每套内部是否保持一致。用户改口“不必用手绘，想更有冲击力”时应调整，不继续锁死黑板。

这些测试区分两件事：人工编排的测试页可以证明播放器和检查工具适配不同布局，但不能证明技能在独立生成中稳定选择了好设计。后者需要真实生成样本和用户反馈。不要混淆两者。

## 参考、默认与硬规则

单文件与不保存脚本是用户明确的交付偏好。16:9、手动播放是当前工作流默认，可被本次要求调整。配色、字体、装饰、布局和动效强度是设计选择，不应由一张参考图决定所有任务。
