# 产品规划：从个人内容工作流到可持续使用的 AI 产品

[返回项目](../README.md) · [MVP](#mvp-定义首版验证什么) · [需求池](#需求池与版本排期) · [阶段路线图](#从-0-到-1到-10再到-100) · [指标与实验](#指标体系与阶段验收) · [技术架构](architecture.md)

我希望解决的是独立创作者从资料到交付的制作负担：既要理解内容、制作不同素材，又要处理修改、事实核查与版本关联。产品以“一期约定的交付”为单位，将研究、生成、修改与验收组织为可复用流程。

**当前阶段：已跑通个人真实任务，正在从 0→1 的可用探索进入 1→10 的稳定复用。** 已有四类输入与实际产物，部分失败处理和交接检查已经落地；跨任务交付率、新用户独立使用与商业模式仍需验证。本文将现有实践、当前需求决策和后续阶段规划放在同一条发展线上。0、1、10、100 表示产品成熟阶段，不是已达到的用户数量。

## 需求规划：先解决谁的什么问题

### 优先用户与切入场景

优先服务**已有内容判断、需要反复制作科技讲解或自有产品内容的独立创作者**。他们通常已有视频、口播稿或产品资料，能够判断表达是否合适，但要在多种素材之间重复交接信息。当前直接使用者是我；相似创作者是下一阶段待验证用户。

| 用户类型 | 任务特征 | 当前选择 |
| --- | --- | --- |
| 有原始材料的独立知识 / 产品创作者 | 有明确主题，需要图文、演示、标题和封面，愿意参与编辑 | 优先：输入与交付较明确，可以观察 AI 是否减少制作负担 |
| 需要持续选题的创作者 | 方向明确但当期主题未定，需要来源和判断依据 | 覆盖研究入口；选题是否被采用单独验证 |
| 尚未形成主题和内容判断的新手 | 同时需要定位、选题、创作指导与工具学习 | 暂不作为首轮扩展对象，避免将定位问题和工具可用性混测 |
| 多账号机构或内容团队 | 需要协作、权限、审核、排期和平台运营 | 后续场景；当前单人产品不承担协作系统复杂度 |

这个切入点能让价值验证落在具体任务上：同一份输入，能否更少返工地得到可使用材料。暂不以“做了更多 AI 内容”或“提升流量”作为首版承诺。

### 从使用信号形成需求判断

| 使用信号 | 背后的需求 | 产品响应 | 证据与影响 |
| --- | --- | --- | --- |
| 图文八页改六页，仍要求只看图就懂 | 能在生成前调整信息结构 | 分析、正文与图片规划分开，确认规划后出图 | [原始反馈](../demo/content-workflow/2026-08-27-literature-review/conversation-excerpts.json)；决定规划确认点 |
| 已有 StayWord 实机演示，只需文案封面 | 接续已有工作，不重复生产 | 按本次交付集合调用 Skill | [部分任务](../demo/script-workflow/2026-09-25-partial-task/README.md)；决定模块可独立调用 |
| 改稿后演示仍沿用旧内容 | 修改需要传到依赖素材 | 记录确切路径、文件版本并提示复核 | [版本修订](../demo/script-workflow/2026-10-16-version-alignment/README.md)；决定交接检查 |
| 产品稿评分通过，但部分主张缺乏依据 | 可发布表达需要事实支持 | 对照产品资料检查具体主张 | [九项主张核查](../demo/content-agent/2026-10-16-draft-review/README.md)；决定质量优先级 |
| 采集成功却没有素材，发布失败掩盖已保存稿件 | 成功状态应对应可用成果 | 区分研究有效性、保存、验收和发布 | [运行诊断](../evaluation/2026-10-17-product-audit/README.md)；决定状态与恢复需求 |

以上来自个人使用、文件与运行记录，足以支持具体交互改进。下一轮研究重点是确认：相似创作者是否也有这些阻碍、现有替代方法是什么、修正负担是否值得更换流程。先观察真实任务，再验证方案。

### 为什么选择工作流形态

| 方案 | 能解决什么 | 没有覆盖的代价 | 我的选择 |
| --- | --- | --- | --- |
| 临时对话，逐次生成 | 启动轻量，适合一次性任务 | 要重复说明要求，难以关联多份产物和修改 | 保留为实验基线 |
| 单项生成工具 | 某一产物制作便捷 | 创作者仍承担主题、事实与版本交接 | 可作为工具能力接入，交付逻辑由工作流组织 |
| 可组合 Skill 与程序 | 复用稳定约定，承接本地材料，允许局部修改 | 仍有环境、路径与模块选择成本 | 当前形态，先验证任务闭环 |
| 一体化云平台 | 可统一入口、资产与调度 | 需要账号、权限、计费、存储和运维 | 只有独立使用与重复需求得到验证后再评估 |

四个模块按输入确定性划分：视频需要先理解，原稿已有表达顺序，产品稿受事实与账号约束，热点线索需要筛选。它们共享交付标准，各自保留适合任务的控制点；雷达不必成为每次制作的前置步骤。

## MVP 定义：首版验证什么

**价值假设：**对已有明确材料和交付目标的创作者，固定上下文、阶段交接与局部修改能够减少重复说明和返工，并保持内容质量。首版要验证这一假设，而非一次覆盖所有内容生产和运营功能。

这里将已有原型收敛为可验收的 MVP 范围；不将后来补齐的检查倒写为最初版本已具备。

| 范围 | 纳入内容 | 为什么必须 / 为什么暂缓 |
| --- | --- | --- |
| 必须：任务约定 | 明确本期输入、受众、所需产物、已有素材、禁止编造的事实与参考要求 | 否则无法判断是否完成，也无法公平比较成本 |
| 必须：选定路径完整运行 | 四种任务入口可选；一次只验收约定路径，不要求四模块全部执行 | 让复杂度随任务变化，支持完整制作与局部补充 |
| 必须：人工可控制 | 出图前改规划、编辑正文 / 标题、单独重做失败素材、决定是否采用 | 内容判断和偏好不能由模型分数替代 |
| 必须：实际交付与恢复 | 返回文件位置、核对必需产物、保存可用部分、解释失败原因 | 用户拿得到成果，局部失败可继续处理 |
| 必须：最低质量与投入记录 | 事实 / 版本 / 规格分别验收，记录调用、等待和人工修改 | 验证工作流产生的是可用交付，而非更多输出 |
| 后续：使用便利 | 示例任务、环境诊断、统一任务入口、标准交接记录 | 支撑新用户独立使用；当前仅有分模块指南与部分检查 |
| 暂缓：规模功能 | 跨模块自动调度、账号与团队、自动发布、平台增长归因 | 尚未验证连续使用需求；会引入额外成本与错误传播 |

**首个价值时刻：**创作者拿到一份符合本次约定、可以编辑或直接取用的材料包；不是第一次生成文本，也不是运行退出码为零。

例如，已有演示、只要求文案与三比例封面的任务，完成条件是文案表达与当前稿件一致，三张封面内容和规格合格，文件路径可直接取用。没有新增演示不影响完成；缺一张必需封面或沿用旧标题则仍未完成。

### 当前 MVP 已有与待补

已有：四类实际产物、规划和局部修改路径、有限审改、部分成果保留；script-workflow 已建立六文件交接检查。待补：跨模块统一任务记录、语义事实校验、研究空结果状态、任务预算和持续验收基线。已有图文原图的比例问题说明，仍需将文件验收贯彻到每次交付。

## 需求池与版本排期

排序先看错误后果和任务阻断，再看证据、依赖与维护成本。下表的 M0–M3 是本产品规划的里程碑，**不是原仓库的历史版本号**；不分配团队职责，按单人可交付范围推进。

| ID / 里程碑 | 需求与用户价值 | 优先级、依赖与取舍 | 当前状态 / 验收出口 |
| --- | --- | --- | --- |
| R01 · M0 | 按输入选择路径，明确本次交付，避免重复制作 | 必须；先于生成 | Skill 约定和部分执行已有；受众、输入版本、产物集合都明确 |
| R02 · M0 | 共享分析 / 当前稿件，保留规划和局部修改 | 必须；依赖 R01 | 已有实例；八页改六页、改标题后改封面可接续 |
| R03 · M0→M1 | 保存成果与失败分开，任务中断后有继续位置 | P0；先保住材料 | 保存计数与失败报告已修复；统一状态记录待补 |
| R04 · M1 | 核对输入、产物、规格与依赖版本，减少错交文件 | P0；依赖 R01 | 口播路径已有指纹检查；其余路径待补，变更后明确哪些产物需复核 |
| R05 · M1 | 按主张核对来源、否定与功能边界，减少错误承诺 | P0；资料依据先于模型打分 | 规则探针已暴露误报漏报；语义校验待做，高影响不支持主张阻断交付 |
| R06 · M1 | 区分研究空结果、缺汇总和有效素材 | P0；先于新增研究调用 | 已定位问题；状态重构待做，空结果不能进入“研究充分”状态 |
| R07 · M1 | 任务级预算、重试与局部重做，控制一次交付总投入 | P1；依赖任务记录和用量归集 | 只有局部轮次 / 超时控制；统一预算待做，达到预算停止并保留成果 |
| R08 · M2 | 示例任务、环境预检与产物索引，降低首次使用成本 | P1；依赖稳定路径 | 分模块 Quick Start 已有；一键预检与统一索引待做，新用户可独立完成首单 |
| R09 · M2 | 自愿提交任务反馈与本地汇总，测量采用和修正负担 | P1；依赖验收定义 | 尚未实施；不上传原稿、人像或未授权素材，区分拒绝共享与任务失败 |
| R10 · M2 | 提示词 / 模型版本回归与回退，避免升级损坏旧任务 | P1；依赖固定样本与预算 | 局部工程回归已有；完整模型变更评测待建，新版本可与旧版对照 |
| R11 · M3 | 统一入口与可选编排，降低多任务操作成本 | 条件进入；依赖 R08–R10 | 规划；以新用户入口卡点或频繁连续任务为触发，不先合并全部工程 |
| R12 · M3 | 可分发能力包、支持方式与商业模式 | 条件进入；依赖重复使用和单位经济性 | 规划；先验证主动复用、接入成本与付费意愿，再决定托管或售卖方式 |

不进入当前排期：强制自动发布、增长承诺、团队协作与大规模渠道扩张。它们需要新的权限、数据与维护设计，不能用当前个人案例直接外推。

### 单人推进顺序

先冻结任务和验收记录，再完善版本 / 规格检查与有效性状态，随后补事实控制和总预算；稳定后才试用新用户入口。M1 中每次只改变一类问题，保留上一版运行样例作为回退依据；不并行铺开新 UI、调度平台和更多模型供应商。

## 从 0 到 1、到 10、再到 100

| 阶段 | 要解决的核心问题 | 产品形态与交付 | 进入下一阶段的依据 | 当前进度 |
| --- | --- | --- | --- | --- |
| **0→1：证明一次任务值得被产品化** | 谁遇到什么反复阻碍，AI 工作流能否交付有用材料？ | M0：个人任务、四类入口、可编辑产物、人工接管 | 有输入—修改—产物的完整实例，能解释替代流程与失败 | 已有个人任务与产物，MVP 质量验收仍需收敛 |
| **1→10：从偶尔可用到稳定复用** | 换主题、改要求或局部失败后是否还能完成？别人能否独立使用？ | M1 先稳定交付；M2 再补接入、评测与反馈 | 正常与变更任务通过验收；异常有正确出口；新用户能首用并主动再用 | 当前投入阶段，尚无外部采用率 |
| **10→100：使使用和维护成本可持续** | 能否复制到更多用户与场景，又不放大支持和模型成本？ | M3：版本化能力包、可选统一入口与编排、适合的交付 / 收费方式 | 复用需求稳定，支持成本可控，质量回归能守住体验，付费或自用收益成立 | 条件规划，未开展规模化运营 |

规模化不必等于重建 SaaS。若创作者愿意在自己的 Agent 环境中使用，先分发版本化 Skill、示例与检查器；若接入和模型配置成为主要阻碍，再评估托管入口。架构形式跟随被验证的使用方式。

## AI 方案如何支持产品阶段

| 产品要求 | 当前实现与取舍 | 后续增强条件 |
| --- | --- | --- |
| 理解来源后再创作 | 字幕优先、无轨道时经确认用 Whisper；正文与卡片共享分析 | 将识别误差与下游事实错误分开测，再决定是否升级获取方式 |
| 稳定规则可复用，本期修改可接续 | 固定账号 / 产品文件与当期分析、原稿、文案分开维护 | 资料规模与查找负担增加后再比较检索；当前不是向量知识库 |
| 风格与身份受控 | image_gen 接收人像与主设计参考，多画幅独立构图 | 用实际文字、身份与规格验收决定重做，不依赖“已成功”回复 |
| 修改有终点 | JSON / Schema 校验、有限审改、瞬态重试、局部图片修订 | M1 汇总跨层请求与支出，避免局部限次叠加为失控预算 |
| 用户能纠正和继续 | 规划确认、正文编辑、局部重做、部分成果保留 | M2 规范统一任务记录，M3 才考虑自动传播和编排 |

**产品边界：**模型处理理解与表达，程序处理确定性约束，创作者决定内容是否采用。人工检查是使用步骤；content-agent 当前需用 `--no-publish` 限定草稿路径，并没有强制的人工发布批准机制。详细配置、数据路径和失败分支保留在[原架构](architecture.md)。

## 指标体系与阶段验收

### 用什么衡量产品，而不是调用次数

核心指标是**约定交付完成率**：全部必需产物通过验收的任务数 / 开始前登记的交付任务数，包含失败与放弃。雷达的交付是合格的来源报告与候选建议；是否继续制作另记采用，不能算成已完成内容制作。四类任务分别报告，不用雷达成功掩盖图文失败。

| 层次 | 指标定义 | 决定什么 |
| --- | --- | --- |
| 首次价值 | 体验者无代操作完成首次合格交付的比例；接入准备时间、开始任务到取用的时间分别记录 | 环境预检、入口和默认模板是否需要改 |
| 任务价值 | 合格交付率；直接采用 / 修改后采用 / 放弃 | 工作流是否产出有用材料 |
| 效率 | 与同类任务基线配对的主动操作与修正时间；工具等待单列 | 确认和返工是否抵消生成收益 |
| AI 质量 | 高影响不支持主张、错版本、缺产物、不可读或规格错误逐类记录 | 改资料、模型、工具还是交接 |
| 重复使用 | 有第二次同类制作机会的人中，主动再次使用的人数；按任务周期观察 | 场景是否成立，是否值得扩大获取 |
| 总成本 | 含失败与重试的生成费用 / 合格交付数；另报人工修正、接入与支持时间 | 是否值得增加研究、审改、自动化或托管 |

目前已有文件、日志和 AI 辅助边界诊断，采用、主动时间与新用户复用需要下一轮研究。指标定义不作为已经取得的成绩。

### M1：交付稳定性与 AI 增益

以下数量与门槛是**下一轮预设的产品验收目标**，不是历史结果或行业基准。

- **交付样本：**四类路径各一条正常任务、一条需求变更任务，共八条；另设四条输入不足或工具失败样本。正常任务与异常处理分别报告。
- **进入 M2 的目标：**八条交付任务至少七条达到约定标准，逐路径列出失败；四条异常样本均正确停止或保留可用成果；不得出现未识别的关键事实错误、原文件损坏或误发布。异常安全退出不计为成功交付。
- **AI 增益对照：**图文、口播和产品稿使用相同资料、模型、可用工具与交付要求，比较临时对话制作和当前工作流，平衡执行顺序；逐项检查事实、版本与规格，再记录人工修正、等待、模型用量和采用。雷达单独比较逐站收集与多源报告，在同一批来源快照上评价漏项、回查负担和选题采用。首次目标是降低主动修正负担，质量同时保持。
- **改进与回退：**已用于修复的样本继续做回归，补未参与修复的新材料验证。若流程增加操作且未减少返工，简化确认；若研究空结果较多，先调整研究入口；若审改消耗增加而事实不改善，减少无效循环。

已有诊断解释为何当前不能直接扩大使用：BirdTracker 高分稿仍有四项主张需调整；十二条构造规则探针有三条误报和三条漏报；九次有汇总的策略采集中六次没有创作者或笔记；另一条五轮审改运行仍未通过。[样本、用量与结果](../evaluation/2026-10-17-product-audit/README.md)

### M2：新用户可用性与复用

计划先邀请五位有明确材料、未来两周有两次制作计划的相似创作者，用受控体验包做诊断性试用。每人先完成适合自己输入的一条路径，再在第二次真实任务中自行决定是否使用。记录必要协助、失败原因、采用方式与退出原因；这不是已经完成的用户研究。

初步扩展条件：至少四人不依赖代操作完成首次交付；至少三人在有第二次制作机会时主动再用。无法按期出现第二次任务的人列为未完成观察，不计流失。样本只用于决定是否继续投入，后续换一批参与者验证，不宣称已证明产品市场匹配。

若首次接入困难但采用结果好，优先做预检与入口；若首用顺利却不再需要，重看场景频率；若总要大量人工修正，回到 M1。留存问题要先归因，不能一律用通知或增加功能解决。

## 增长与商业化规划

### 先让合适的人取得第一次价值

获取材料应展示一个具体输入、修改过程和完整交付，例如原稿如何变成演示、文案与三比例封面。体验包配一条无需用户自带敏感资料的示例任务，标明所需宿主、模型和环境；再引导使用者带入自己的任务。当前仓库仍保持私有，外部试用与公开分发尚未执行。

计划按“了解样例 → 完成环境准备 → 首次交付 → 实际采用 → 第二次任务”观察转化。若在准备阶段流失，改善接入；若看到结果却不采用，回到内容质量和需求匹配；有稳定复用之后才扩大内容渠道或考虑付费获取。分享与作品展示由使用者决定，不自动上传素材或向他人发送消息。

### 商业形态随成本结构选择

| 可能形态 | 适用条件 | 必须核算的成本 |
| --- | --- | --- |
| 个人效率工具 | 自用价值成立，外部需求尚未验证 | 维护、模型与人工修正投入是否低于实际任务收益 |
| 用户自带模型的能力包 | 能独立接入，愿意为稳定流程、模板与更新获得服务 | 安装支持、版本兼容、持续维护；用户仍承担模型费用 |
| 托管任务服务 | 接入门槛是主要阻碍，重复使用和付费意愿已验证 | 全链路推理与图片费用、失败重试、存储、支持和内容数据管理 |

定价先验证使用者愿意为何付费，以及接入和支持需要多少投入，再用完整成本记录选择收费方式。托管模式可用“每个付费合格交付的收入 − 对应全部变量成本”观察贡献；原始 Token 或单次成功调用成本不能代表单位经济性。
