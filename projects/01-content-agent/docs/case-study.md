# 内容生产 Agent 与 Skill 工作流：从生成内容到交付任务

个人创作中，AI 已经能生成正文、图片和演示，但一期内容还需要选题、组织素材、反复修改，并判断结果能不能用。我围绕自己的实际任务，将这些工作整理为四个可独立调用的板块：content-workflow、script-workflow、content-agent、daily-trend-radar。

项目独立完成需求梳理、流程设计、实现与迭代。以下用真实任务解释产品判断；方案比较和优先级是当前复盘，历史输入、产物及本轮修订分别保留。[查看项目首页与成果](../README.md)。

## 1. 问题不止是生成慢，还包括任务难以接续

本项目的直接使用者是我自己，最终内容面向科技与知识内容读者、以及自有产品的潜在用户。已有材料能证明具体创作需求，尚不能代表其他创作者的使用频率或市场规模。

| 真实需求与事件 | 对产品的要求 |
| --- | --- |
| 视频图文任务要求八张改六张，并且只看图片也要能理解 | 允许重组信息密度，图片与正文分别完成表达 |
| 已有实机演示的一期只需要文案和封面 | 按本次需求选择交付，跳过已完成环节 |
| 文案手动修改后，又要求调整封面的标题和设计 | 后续产物读取当前输入，修改能沿依赖继续 |
| 草稿通过模型审稿、保存后，发布准备失败 | 区分内容判断、文件保存和发布结果，保留部分成果 |

这些观察使我把产品目标放在“完成一次可接续的内容任务”上：开始时确定产物，过程中保留可编辑材料，结束时说明哪些已经可用、哪些需要修正。生成速度是需要测量的收益，不作为替代质量的验收条件。

## 2. 用交付范围划分产品，而不是强制跑完整流程

四个板块服务同一创作活动，但起点不同。已有口播稿时不必重新找热点；产品内容要依据产品资料，也不应为了追热点强行套用外部视频主题。因此先提供独立入口，使用同样的交付原则，而没有做统一自动调度平台。

| 板块 | 从什么开始 | 本次任务可以交付什么 | 哪个决定留给创作者 |
| --- | --- | --- | --- |
| content-workflow | 视频与表达要求 | 分析、正文、系列卡片 | 读者角度、卡片规划与最终表达 |
| script-workflow | 本期口播稿、已有素材 | 演示、文案、三比例封面，或其中一部分 | 选择本期范围、编辑标题与判断视觉 |
| content-agent | 产品、账号与研究资料 | 有审改记录的候选稿 | 核实产品事实、决定是否采用 |
| daily-trend-radar | 来源范围与选题方向 | 来源报告与候选角度 | 选择值得继续查证、制作的主题 |

首版范围优先保证三件事：**材料有依据、局部能修改、完成状态可信。** 视频录制剪辑、跨板块自动串联与无人值守发布不作为当前作品集的成果。现有内容 Agent 默认入口仍会尝试发布；本作品集采用 `--no-publish` 限定为草稿交付，尚未实现强制人工批准的统一发布入口。

## 3. 从四类任务中做出的具体选择

### content-workflow：复用理解，分别设计正文与卡片

正文和图片都从 `analysis.md` 获取依据，但各自决定表达方式。这样可以修改卡片数量与信息组织，同时保留完整正文；也可以只修改正文的受众视角。

[文献综述任务](../demo/content-workflow/2026-08-27-literature-review/README.md)保留了八张与六张两版规划。两次具体合并说明了篇幅调整如何落到内容，而非只改变生成数量：

| 八张规划 | 六张规划的处理 | 保留的阅读价值 |
| --- | --- | --- |
| “效率冲击”与“综述的真实目的”分两页 | 合并为“文档完成，不等于研究完成” | 同一页解释 AI 做到了什么、研究者仍需做什么 |
| “提问与反驳”与“貌似可信的陷阱”分两页 | 合并为“提问、反驳，识别貌似可信” | 把风险和对应的检查动作放在一起 |

[八张规划](../demo/content-workflow/2026-08-27-literature-review/plan-original-eight.md)与[六张规划](../demo/content-workflow/2026-08-27-literature-review/plan.md)可直接对照。

**取舍：** 分别从视频生成两套内容，交接少但容易各自理解；把正文机械拆成图片，省去一次规划却未必适合滑读。当前采用共享分析、独立规划，接受一次额外内容检查，也需要防止分析错误同时传给两个分支。

**交付与边界：** 已恢复完整正文、六张生成原图和修改依据，五项核心内容有对应。原图规格不统一，历史最终裁切文件缺失；本次验证的是内容与修改关系，不能记成全套发布规格合格。

### script-workflow：把“已有一部分”视为正常任务

[第 004 期](../demo/script-workflow/2026-09-25-partial-task/README.md)已经完成实机演示，只需要文案和封面。本人又手动修改文案，继续调整封面主副标题。这个场景要求能力可单独调用，已有产物也能成为下一步的输入。

因此演示与文案分别读取原稿，封面承接当前文案。三个 Skill 各自交付明确文件，PPT 与 post 允许独立编号，以真实路径关联本期任务。

**取舍：** 一键全套生成更省选择，但会重复已有工作，也不适合只修改标题或封面。按需调用更贴合实际使用，代价是需要处理不同版本、不同编号的交接。

[第 005 期](../demo/script-workflow/2026-10-16-version-alignment/README.md)暴露了这个代价：演示第 5–7 页仍沿用旧稿。本轮按修订稿调整内容，并增加六文件交接检查。文件变化提醒复核，语义对齐仍要回到原稿。

**交付与边界：** 15 页演示已对齐并检查 42 个播放状态，文案与三比例封面可查看。历史反馈支持部分执行和局部设计认可，不能扩展为所有素材都已最终采纳。

### content-agent：让产品资料约束生成，让事实核对约束评分

产品内容不仅要通顺，还需要准确解释功能与使用边界。我将产品资料、账号语气和平台规则作为持久输入，程序组织研究、写作与最多五轮审改；模型参与语义判断，程序控制结构与停止条件。

[BirdTracker 历史任务](../demo/content-agent/2026-07-09-birdtracker/README.md)经过两轮审稿，分数从 8.4 到 8.6 后通过。本轮再依据产品资料核查九项主张，仍发现四项需要删除或调整，例如将热点地图写成能找到鸟多的地方、把拍照与荣誉页作绝对关联。

**判断：** 模型通过是流程信号，不能直接当成事实正确或用户愿意采用。当前需要同时检查“结构是否完整”“资料是否支持”“读者是否能理解并使用”，不能只优化总分。

**取舍：** 一次生成调用少，但没有逐轮修改反馈；增加审稿有机会暴露问题，也会增加等待与费用，且审稿模型可能漏掉事实错误。当前保留有限轮次与人工复核，尚无证据证明更多审稿轮次一定更好。

**迭代：** [修订候选稿](../demo/content-agent/2026-10-16-draft-review/README.md)移除了无依据表达及混入正文的内部审核说明；代码修复保存成功却计数为零的问题，并修正会引导产品稿加入工具实现说明的改稿提示。确定性回归验证了状态和停止行为，提示修改后的模型质量仍待实际对照。

### daily-trend-radar：从“收集热点”走到“决定值得做什么”

雷达先产出有原始链接、来源状态和时间信息的报告，再形成与读者相关的候选角度。榜单位置用于发现线索，不能直接代表事实可靠或值得制作。

[本次三源报告](../demo/daily-trend-radar/2026-10-16-source-check/README.md)共 15 条，其中 10 条没有发布时间。它们按当前在榜保留，不能包装成当天首发事件。两次直接请求失败后沿用系统代理恢复；全失败也会保留诊断报告。

[选题简报](../demo/daily-trend-radar/2026-10-16-source-check/brief.md)中的选择同时考虑相关性与验证投入：插件目录主题可结合已有 Skill 解释，优先继续；科研 Skill 适合讨论判断边界；上下文工具主题需要另做安装和对照，暂不直接制作教程。

**取舍：** 直接抓取来源便于回查，但需要维护适配器；强制全量覆盖会扩大等待和失败影响。当前允许选择来源、交付部分报告并说明缺失，保留创作者的选题决定。三条建议均来自 GitHub，未当作跨平台共振，也未自动驱动其他工作流。

## 4. AI 能力如何进入产品

这里的设计工作包括任务拆解、上下文组织、交付约定和质量控制。推理与图像生成由宿主或外部模型服务提供，未自研基础模型或宿主运行环境。

**需要变化的表达交给模型，必须稳定的规则交给程序。** 视频理解、改编、叙事与选题需要语义判断；编号、图片尺寸、状态记录和停止条件适合确定性处理。两个 Skill 工作流经常调整读者、风格与产物组合，保留对话式调用；内容 Agent 的审改循环和雷达采集则由 Python / Node 控制。

上下文按用途组织，避免每次只给模型一个模糊任务：

| 上下文 | 实际载体 | 需要控制的问题 |
| --- | --- | --- |
| 稳定事实与规则 | 产品、账号、平台资料；各 Skill 的输入输出约定 | 资料过期会持续影响生成，需要维护与复核 |
| 本期任务与修改 | 原视频分析、口播稿、已编辑文案、图片规划 | 不同版本混用会导致产物分叉，使用明确路径交接 |
| 当前外部信息 | 研究输入、雷达原始报告与来源时间 | 新鲜信息不等于可靠事实，缺失与推断单独标明 |
| 当前结果与反馈 | 草稿、审稿原因、计划修订与生成文件 | 保留修改依据，不只保存最终一句“成功” |

这主要是文件与提示词层面的上下文组织，不是已实现的统一知识库或自动版本管理平台。当前也没有模型横向评测，不能宣称使用了最优模型。

## 5. 如何判断项目有效

首先按本次任务约定验收。例如只要求文案和封面时，没有 PPT 是范围选择；要求三比例封面时，缺一张则不能算完整交付。任务状态、内容质量和用户采纳分别记录。

| 核查对象 | 已有观察 | 能支持的判断 |
| --- | --- | --- |
| 图文表达 | 两版规划、正文与六原图，五项内容覆盖 | 能解释篇幅调整与双分支表达；最终裁切规格仍缺失 |
| 口播素材 | 修订稿与演示对齐，15 页／42 状态，三封面规格 | 本期素材关系与播放可检查；尚无跨任务采纳率 |
| 产品草稿 | 九项主张逐条复核，四项删除或调整 | 评分之外需要事实审核；不将此比例推广为模型错误率 |
| 热点研究 | 三源 15 条报告、失败恢复与选题理由 | 一次交付可追溯；长期来源稳定性和选题采用率未知 |

工程相关的 29 项测试支持具体实现行为，详细范围见[验证记录](../evaluation/release-review.md)。它们不作为产品效果指标。

下一轮的测量围绕产品决策，而不是继续累积生成数量：

- **交付与采纳：** 分母包含预先登记的成功、失败和放弃任务，按实际要求检查全部产物，再由本人确认是否采用。
- **修正负担：** 将事实、主题、视觉和规格问题分开，记录主动操作时间；会话跨度不能代替人工时间。
- **单个合格结果成本：** 计入失败、重试、图片和转写支出，再除以合格结果数；没有合格结果时不计算单价。

现有记录未覆盖上述完整测量，不能补写节省比例、ROI 或增长数据。

## 6. 下一步投入顺序

| 优先级 | 依据与动作 | 什么结果会改变安排 |
| --- | --- | --- |
| 先解决事实与版本问题 | 已出现无依据产品表达与演示旧稿；保持事实复核、明确输入和交接检查 | 如果错误来自基础资料，先改资料；如果来自修改传递，再完善交接 |
| 再衡量规划与审稿的价值 | 对固定要求保留计划、初稿、改稿与失败，记录人工修正和总费用 | 规划未减少结构返工则改为按任务触发；分数提升而事实未改善则先改审核依据，不加轮次 |
| 最后决定是否自动串联 | 观察雷达候选是否进入创作、还需补多少资料 | 候选频繁替换或补证成本高时，继续人工选题，只标准化交接 |

这个项目目前体现的是将个人真实任务转成可运行、可检查的 AI 产品流程。面向更多创作者时，仍需要验证任务是否共通、交付方式是否易用，以及这些流程是否值得他们持续采用；商业化与规模化能力不能由现有个人样本推出。

## 7. 下一轮怎样验证这些设计是否值得保留

已有案例证明了任务与问题确实发生过，还不能证明“工作流比直接对话更好”。下一轮将围绕三项具体假设设计对照，而不是继续增加演示数量。以下是待执行的验证方案，没有实验结果。

| 要判断的投入 | 对照方式 | 判定依据与后续动作 |
| --- | --- | --- |
| 出图前规划是否值得 | 同一视频、同一交付要求，比较直接生成与先规划；使用相同模型和生成规格 | 记录结构返工、人工操作时间及总费用。若只增加确认而不减少返工，改为结构复杂或要求变化时触发规划 |
| 多轮审稿是否值得 | 固定产品资料与主题，保留一次生成和有限审改的全部稿件；由人按同一事实清单验收 | 比较事实错误、人工删改与合格稿成本。若分数增加而事实不改善，先完善依据和审核规则，不增加轮次 |
| 雷达是否值得自动接入创作 | 固定报告，先记录候选中实际选择的主题，以及选定前还需补哪些资料 | 若候选经常更换或补证工作多，继续人工交接；只有能稳定产出可进入制作的输入，再设计自动调度 |

**样本与执行。** 首轮为小规模、单人探索：图文和产品稿分别预先登记三个不同输入，包含普通任务、要求变化和信息不足场景，各方案在相同配置下重复两次。采用交错运行顺序，保存全部失败与放弃。雷达先固定同一份报告评估判断，再另测跨日来源稳定性，避免把榜单变化混入方案对照。这不能估计市场采纳率，也不能用小样本宣称统计显著优势。

**先过质量门槛，再比较投入。** 不支持的核心事实、错版本、缺少本次要求的产物均视为未达交付标准；视觉或表达需改时记录具体原因。将候选隐去方案标签后人工审阅，仍说明审阅者是同一使用者，存在熟悉效应；模型自评只能辅助定位，不能决定胜负。

| 指标 | 口径 | 为什么需要 |
| --- | --- | --- |
| 约定交付完成率 | 全部必需产物通过对应验收的任务数 / 预先登记的全部任务数 | 避免只统计成功生成，或惩罚正常的部分执行任务 |
| 最终采用情况 | 分别记录直接采用、修改后采用、放弃；记录确认人和时间 | 区分“模型通过”“可以阅读”与“用户真的使用” |
| 人工修正负担 | 事实、叙事、视觉、规格分别记次数与主动操作分钟 | 确认流程究竟节省了什么；会话跨度不能替代操作时间 |
| 单个合格交付成本 | 含失败与重试的可归属总费用 / 合格交付数 | 高通过率可能由高成本换取；没有合格交付则标记未产生，不除以零 |
| 等待与中断 | 每阶段起止、用户主动等待、无必要确认次数分别记录 | 延迟与人工操作是不同体验，额外确认可能抵消自动化收益 |

**从现有任务就能发现的交互改进。** 文献综述任务在用户回复“可以”后，助手仍表示“如果需要，我可以继续”，直到用户再次说“那你继续吧”才推进。原始记录可在[对话摘录](../demo/content-workflow/2026-08-27-literature-review/conversation-excerpts.json)回查。这说明计划确认必须对应真正的范围或方向决策；得到明确继续指令后，再问一遍不会增加判断价值。此处是待改进项，未宣称已经调整所有 Skill 的交互规则。
