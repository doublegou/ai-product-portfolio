# 内容工具链案例初稿

状态：基于现有实现整理的事后复盘框架；用户需求与历史决策动机待本人校正。

## 问题与范围

目标场景暂定为科技内容创作者将外部视频或本人脚本转换为可编辑的发布素材。待确认的核心问题是工具切换、字幕不可用、不同产物规格和人工审查成本。现有工具链可以支持这些任务，但尚无新增访谈证明问题普遍性。

首版展示范围：完成内容素材制作与验收。发布动作单独处理，不以全自动发布作为案例成功标准。

## 能力与状态

| 环节 | 当前来源 | 产品解释 | 待补证据 |
| --- | --- | --- | --- |
| 内容获取 | yt-analysis 字幕脚本 | 优先使用已有字幕，无法获取时再选择转写路径 | 一条字幕正常和一条字幕不可用的实际记录 |
| 分析与生成 | 图文 Skill、content-agent | 分离原始材料、研究输入和创作结果 | 带来源的样例，事实与改写的检查 |
| 质量控制 | review/revise、文件检查脚本 | 格式规则与内容判断分别验收 | 人工评价与模型评分不一致的例子 |
| 输出协作 | post、image、slides | 通过目录与文件约定衔接产物 | 同一期材料从输入到全部交付的记录 |
| 运行观察 | content-agent run_id 日志 | 将失败与执行过程关联到任务 | 样例日志和明确的失败类别 |

## 需要确认的三项取舍

1. 从浏览器操作转向 Skill/脚本的真实触发原因是什么？保留哪些必须由浏览器完成的任务？
2. 谁负责判断内容合格：确定规则、模型审稿与人工分别承担什么？如何避免模型自评代表最终质量？
3. 面对多个输出，什么情况下应共享分析结果，什么情况下应该独立生成？

这些问题由现有实现引出，不能反过来断言它们都是开发前已确定的设计原则。

## 拟补的最小改进

先补一份运行记录，包含任务标识、输入、版本、阶段状态、产物路径、实际成本与人工介入。若实际衔接反复出错，再考虑统一任务标识与入口；本轮未实现统一调度器。

每个待补能力至少说明：用户收益、成功条件、失败时体验和不做的范围。优先记录实际失败，不先扩张平台功能。
