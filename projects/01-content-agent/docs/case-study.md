# 产品设计：把一次内容任务做成可接续的工作流

我从自己的内容创作任务中提炼可复用的步骤，再决定哪些交给模型、哪些用程序控制、哪些保留人工判断。[项目首页](../README.md)展示实际任务，本页复盘这些选择及其代价。

## 1. 产品定位与最小范围

我同时是这套工作流的设计者和直接使用者。使用场景是独立科技内容制作：需要理解外部资料、形成自己的讲述，再制作图文或视频配套材料。最终读者关心内容是否具体、可信、容易理解；创作者则要在有限时间里完成这些表达。

因此，产品的工作单位是**一期约定的交付**。一次模型回复可能只完成其中一步；多个文件同时存在也可能仍然错用版本。我的目标是把重复要求和检查沉淀下来，让新主题与局部修改可以进入相同流程。

### 为什么需要四个入口

| 已有材料与场景 | 使用者最需要解决的问题 | 模块的边界 |
| --- | --- | --- |
| 外部视频值得向中文读者解释 | 先理解原意与依据，再组织正文和独立可读的卡片 | content-workflow 以共享分析连接两种表达 |
| 已有自己的口播稿 | 补齐演示、标题、简介和封面，或者只补其中一部分 | script-workflow 按交付集合调用三个 Skill |
| 自有产品需要具体内容 | 在产品事实、账号定位和平台要求中完成研究与写作 | content-agent 组织上下文与有限审改 |
| 还没有确定下一期主题 | 找到来源、判断相关性、形成可继续研究的角度 | daily-trend-radar 交付来源与建议，由我决定是否制作 |

这四类任务具有不同的输入确定性。原稿已经确定表达，视频需要先理解，产品稿受事实约束，热点线索仍需筛选。因此入口按任务分开，共用交付要求；雷达不是每次创作的必经步骤。

### 最小闭环如何完成

| 环节 | 必须具备的产品能力 | 完成判断 |
| --- | --- | --- |
| 明确任务 | 知道本次受众、输入版本、要哪些产物，以及哪些素材已经完成 | 例如只做文案和封面时，不额外生成演示 |
| 生成 | 将相关资料带入对应 Skill 或程序，保留中间分析与规划 | 输出能沿输入回查，不只有最终成图或一段正文 |
| 修改 | 支持在规划、正文、演示和画幅层面局部调整 | 八页改六页先改结构，标题变化后核对关联封面 |
| 验收 | 检查必需文件、内容依据、表达一致性与具体规格 | 程序检查与人工内容判断各有结果 |
| 取用 | 清楚返回本期路径，保留已完成部分与失败原因 | 创作者能拿到可编辑材料，并知道仍需处理什么 |

这是四个模块共用的设计和使用约定，目前由各自的 Skill、文件与程序落实；没有统一任务数据库或自动依赖传播。script-workflow 已有文件指纹交接检查，其他路径保留各自记录。

**范围控制。** 当前交付止于可取用素材与研究建议。统一工作台、跨模块自动编排、自动更新长期策略、平台增长归因暂不扩展。content-agent 的工程保留发布模块，当前演示使用 `--no-publish`，人工取用尚非程序强制发布闸门。

### 从使用任务到产品规则

我用实际任务检验上述范围。以下是使用与改进的演进，不将某个样例日期当成整个模块的首发日期。

| 使用阶段 | 具体反馈或问题 | 沉淀的产品规则 |
| --- | --- | --- |
| 7 月 · 产品内容 | BirdTracker 草稿经过审改后保存，发布准备仍可能失败；模型高分也不能保证主张可信 | 保存、内容质量、发布分别判断；保留资料和审改依据 |
| 8 月 · 视频改编 | 卡片从八页改六页，仍要求只看图能理解 | 先调整内容结构再出图；正文和卡片共享依据、分别组织表达 |
| 9 月 · 口播素材 | 已有 StayWord 实机演示，只需文案封面；另一期又需要完整三类素材 | 同一套 Skill 支持完整与部分任务，人工改稿可以接续 |
| 10 月 · 交接与恢复 | 演示仍有旧稿内容；发布异常使保存计数失真；全源采集失败未保留报告 | 对齐关联素材、检查文件版本、保存部分成果和失败报告 |
| 10 月 · 质量与成本诊断 | 规则误报漏报、研究空结果、多轮审改投入仍未换来通过 | 下一轮优先验证事实依据与研究有效性，再决定是否增加自动化 |

各阶段的对话、日志与产物均从[四类实际任务](../README.md#四类真实交付)进入；使用量、采纳率和节省时间尚不据会话数量估算。

### 为什么保留对话与文件入口

已有口播稿、图片和产品资料都在本地，对话入口能承接正在做的工作，文件交付便于编辑与录屏。我先把重复出现的要求固化为 Skill 与程序，避免为每类材料建立新的输入界面。

代价是路径、模块选择和版本关系仍需要理解。若后续首次使用频繁卡在选择入口或查找产物，我会优先做统一任务入口；若主要返工来自错误事实和过时内容，则先改善资料与验收。界面和编排的优先级由任务阻碍决定。

## 2. 方案选择与代价

| 决策 | 备选方案为什么不够 | 当前方案及代价 | 什么结果会改变选择 |
| --- | --- | --- | --- |
| 共享视频分析，正文与卡片独立创作 | 分别理解视频可能分叉；直接把正文拆图未必适合滑读 | 先沉淀分析，再分别组织表达；增加一次规划检查，错误分析也可能同时影响两个分支 | 如果规划没有减少结构返工，改为复杂或变更任务才触发 |
| 按需调用素材 Skill | 强制全套生成会重复已有演示，也无法高效处理只改标题 | 允许局部生成；承担多文件版本关联成本 | 若多数任务始终成套且几乎无局部编辑，再考虑默认串联 |
| 程序控制审改，模型处理语义 | 单次生成缺少反馈；无限审改成本与停止时间不可控 | 规则筛查＋模型审稿＋最多五轮；模型仍可能自洽地接受错误事实 | 若审改未降低人工事实修正，优先改资料和审核依据，不增加轮次 |
| 报告与选题判断分开 | 热榜标题直接进入写作，容易把热度当成价值或真实性 | 保留来源与时间，回查后再筛角度；增加编辑判断 | 若候选稳定进入制作且补证较少，才适合研究自动交接 |

这些选择构成同一项目的产品逻辑。四个模块既覆盖创作活动，也保留不同任务的完成条件；没有为了凑成一条流水线而要求用户先找热点再改编视频。

## 3. AI 系统设计：上下文、控制与接管

| 设计对象 | 当前实现 | 关键风险与控制 |
| --- | --- | --- |
| 稳定上下文 | 产品资料、账号规则、平台规范；Skill 的输入输出约定 | 资料错误会反复传入生成。核查先追到产品依据，不只修改措辞 |
| 任务上下文 | 视频分析、修订口播稿、当前 post.txt、图片规划 | 原稿变化后，显式传入确切文件；交接检查发现变更，人工再判语义 |
| 动态研究 | 榜单、写作研究与策略采集结果 | 来源缺失、空结果和时间未知必须可见，不能被成功退出码覆盖 |
| 模型判断 | 创作、审稿、改稿与选题角度 | 模型评分用于定位和迭代；具体主张还要对照依据 |
| 程序控制 | 结构校验、文件规格、审改上限、持久化与失败诊断 | 程序检查通过只说明对应规则满足，不包办事实与视觉质量 |

我将稳定背景与本期任务分开维护。内容 Agent 当前加载四份固定账号／平台文件和产品 Markdown，使用文件式上下文。只有资料规模、查找成本或版本更新开始阻碍任务时，才值得比较检索方案；模型替换也需要用同输入的质量与成本对照决定。

**人如何接管。** 图文在出图前确认结构，口播素材在播放和编辑时修正，产品稿在取用前核查主张，雷达在进入制作前选题。实际使用时，我已确认继续，助手却再次询问，打断了任务。因此确认应集中在范围或方向变化处。[原始记录](../demo/content-workflow/2026-08-27-literature-review/conversation-excerpts.json)支持这一交互改进方向。

模型、工具执行和人工环节的实际边界详见[架构](architecture.md)。

## 4. 质量评估如何改变产品判断

我结合文件验收、运行日志和 AI 辅助规则探针定位不同层面的质量问题。全部输入与统计实现见[2026-10-17 产品评测](../evaluation/2026-10-17-product-audit/README.md)。

**评分可能选错优化方向。** BirdTracker 历史草稿达到内部总分门槛，九项主张仍有四项需要调整。新构造的 12 条规则探针又发现：直接承诺会被拦截，否定承诺也可能被误拦，同义风险却会漏过。当前应优先检查“主张—资料”关系；提高模型总分门槛不能直接解决这个问题。

**成功状态可能掩盖无效研究。** 十次历史策略采集均为 success，九次有汇总，其中六次创作者与笔记均为零。需要将技术完成、素材可用和最终交付分开。空结果可以触发换查询、换来源或仅依据已有资料继续，但必须向用户说明本次没有新研究依据。这是待实现的降级设计，未作为现成功能展示。

**更多审改可能只增加消耗。** 一条保存草稿的运行有 6 次完整用量记录，合计 102,306 Token；另一条五轮仍未通过，已知用量至少 121,611。两个任务不足以证明审改因果效果，但足以提出成本问题。输入占前者 Token 的约 87.8%，下一步应检查上下文是否重复，再做质量保持实验，不能先承诺降本。

### 指标体系

| 层级 | 指标与分母 | 用来做什么决定 |
| --- | --- | --- |
| 核心结果 | **约定交付完成率**＝全部必需产物通过验收的任务数 / 预先登记的全部任务数 | 判断工作流是否真的完成用户任务；分母含失败与放弃 |
| 用户价值 | 直接采用、修改后采用、放弃；主动修正分钟 | 判断收益来自哪里，确认与返工是否抵消生成速度 |
| 内容质量 | 不支持的主张、错版本、缺素材、不可读／规格问题，逐类记录 | 定位需要改模型、资料、交接还是工具；不合成含义不明的总分 |
| 成本与等待 | 含失败重试的总支出 / 合格交付数；运行耗时与人工操作时间分开 | 在质量门槛满足后比较投入；没有合格结果时单价不适用 |
| 运行诊断 | 来源成功数、空结果、调用数、Token、各阶段耗时 | 解释失败或投入来源，不能代替上面的产品指标 |

采纳与主动时间目前缺记录，不能从文件数量反推。费用报告只提供已记录用量与明确假设单价的敏感性分析；它不等于账单，也不覆盖图片和人工成本。

## 5. 迭代优先级：先降低错误交付，再验证效率

优先级依据错误后果、已有证据与验证成本，不以未经调研的覆盖人数套算 RICE。

| 顺序 | 下一项工作 | 验收条件 | 当前状态 |
| --- | --- | --- | --- |
| P0 | 事实校验按具体主张核对支持资料，保留不确定项 | 降低已知误报和漏报；新增未用于修改的保留样本，防止只适配现有 12 条 | 已定位问题，语义校验尚未实现 |
| P0 | 策略采集增加结果有效性状态 | 无结果、缺汇总、有效素材能区分；失败保留诊断和已有材料 | 历史审计完成，状态重构待做 |
| P1 | 把版本交接用于后续实际创作 | 改稿后能够识别需复核的演示、文案与封面，记录是否遗漏 | 已有指纹检查，跨任务验证待做 |
| P1 | 固定输入比较直接生成与有限审改，同时记录上下文用量 | 先比较事实与采纳，再比较修正时间和合格交付成本 | 实验方案如下，尚未执行 |
| P2 | 评估雷达与创作是否值得自动交接 | 记录连续任务中候选采用与补证负担；证据不足则继续人工选择 | 当前独立使用 |

当前版本已修复保存计数、全失败报告留存和改稿提示偏题，并完成相关工程回归。边界探针发现的新问题没有被“29 项工程测试通过”覆盖。

## 6. 验证方案：先过质量门槛，再比较投入

以下是下一轮方案，不是已取得的实验结果。

**设计。** 图文与产品稿分别预先登记三个输入：普通任务、要求变化、信息不足。每个输入比较“直接生成”与“当前工作流”，每种方式重复两次；固定资料、模型配置、交付要求，交错运行顺序，保存全部失败和放弃。图文重点比较规划是否减少结构返工；产品稿重点比较审改是否降低事实修正。

**判定。** 核心事实无依据、错用版本、缺少必需产物，均记未达交付标准。隐去方案标签后按同一清单检查，记录直接采用、修改后采用、放弃，以及事实／叙事／视觉／规格的主动修正时间。审阅者仍是同一使用者，结果仅用于个人产品探索，不声称盲测完全消除了偏差或达到统计显著。

**决策。** 审改得分升高而事实没有改善时，先改审核依据；规划增加确认却不减少返工时，只在复杂任务开启。各方案均过质量门槛后，再对照总费用和修正时间，避免用低质快稿证明效率。

雷达分开验证两个问题：固定同一报告比较候选是否值得制作；另做跨日采集验证来源稳定性。将榜单变化、采集可用性和编辑价值混在一起，会无法判断究竟要优化哪一层。

## 扩展使用前，先验证什么

当前已经验证了个人任务的输入、修改和交付方式。扩展到其他创作者时，我会先看他们能否独立选对入口、提供必要资料、找到产物并完成修改，再研究长期采用与付费；不把个人任务中的顺手程度直接当作普遍需求。

成本上，我关注**完成一期内容的总投入**：文本、图片、重试、工具等待与人工返工。单次调用更便宜却产生更多修改，未必降低交付成本。内容 Agent 的五轮上限只约束审稿循环，结构纠正和传输回退还会增加请求；统一任务预算是后续设计，当前不能仅按五轮估算费用。

优先投入的条件是能减少事实修正、重复制作或失效交接；统一编排需要进一步证明模块间材料经常连续使用。这样，产品范围随真实任务增长，而不是随可接入工具的数量增长。
