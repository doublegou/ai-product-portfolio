# daily-trend-radar：把多源榜单整理成可判断的选题输入

我用 daily-trend-radar 收集公开榜单，统一条目、归并候选事件并记录来源状态，再由 Agent 辅助回查与形成选题建议。它服务内容制作之前的研究判断。

[整体产品设计](case-study.md) · [实际来源与选题简报](../demo/daily-trend-radar/2026-10-16-source-check/README.md) · [采集记录](../evaluation/2026-10-17-product-audit/radar-live-runs.json)

## 1. 使用场景与问题定义

设计服务需要跨平台观察 AI、科技和开发者动态的个人创作者。一次选题准备需要回答：发生了什么、哪些事件值得关注、是否与本次受众相关、结论能回查到哪里。

从任务拆解看，逐站浏览要重复打开榜单、收集链接、辨别重复事件并判断时间。单看某个平台的排名，会遗漏其他来源；直接汇总各站热度数字，又会把不同口径当成同一种指标。模型仅凭记忆回答“今天发生了什么”也缺少可核对的实时依据。

产品设计因此优先解决来源可追溯、时间语义正确和不完整结果可识别。榜单热度用于发现线索，不能直接替代事实核实和受众判断。

## 2. 产品目标与完成条件

目标是在明确来源范围内，交付一份可核查、可筛选、能说明缺失情况的选题输入。

| 优先级 | 要解决的事 | 首版验收条件 |
| --- | --- | --- |
| 必须 | 来源可回查 | 重要条目保留原始链接、来源与抓取时间 |
| 必须 | 时间不误导 | 发布时间未知时明确未知；抓取时间不冒充事件发生时间 |
| 必须 | 失败可见 | 每个实际请求来源有状态；部分失败时明确标记覆盖范围 |
| 必须 | 跨源可比较 | 标准化字段，候选重复事件经语义复核；不直接比较异构热度值 |
| 必须 | 建议有依据 | 区分事实、推断和创作角度；说明与任务或受众的关联 |
| 后续验证 | 维护成本可控 | 记录来源健康度、误归并、失效原因与实际使用价值 |

当前配置为 15 个平台、18 个榜单入口，这只是适配范围；实时覆盖需要单独测量。首版不承诺全网完整覆盖、自动事实核查或自动发布。

## 3. 使用过程与交付

```text
选择预设／来源 → 按平台调度采集 → 标准化条目
              → 时间过滤 → 候选事件归并 → 报告与来源状态
              → Agent 核对语义、判断相关性、形成选题建议
```

输入为来源范围、条数、时间过滤和输出格式；输出支持 JSON、Markdown、CSV。程序处理固定字段与报告，Agent 做语义判断，我决定是否采用某个选题。下游使用报告时明确传入的文件及时间，避免把旧报告当成当前热点。

fetchedAt 表示获取时间；缺失 publishedAt 的条目只能说明当前在榜。标题相似只是候选事件归并，最终是否同一事件需要看链接与内容。跨源出现也不自动证明新闻真实。

## 4. 方案选择与代价

| 设计问题 | 当前方案 | 可比较方案与代价 |
| --- | --- | --- |
| 如何取得信息 | 直接读取各公开来源，保留适配器 | 第三方聚合入口更集中；直接来源便于追溯，但页面和接口变化增加维护 |
| 如何兼顾范围和可用性 | 可选预设，逐源报告状态 | 每次强制全量覆盖更简单，但等待与失败更难控制；可选范围需明确报告覆盖边界 |
| 如何处理重复事件 | 程序给候选分组，Agent 再判断 | 全人工归并工作多；完全自动归并可能误合并，当前方式需人工抽查 |
| 如何处理异常 | 单源失败保留其他结果，全失败明确报错 | 任一失败就终止会丢弃可用信息；部分报告则必须说明缺失 |
| 如何接入创作 | 先保留独立报告与人工交接 | 直接自动驱动内容生产更连贯，但相关性、时效与数据适配尚未验证 |

同平台顺序调度用于控制同时请求数，不代表已解决限流；遇到访问限制按工具现有规则记录状态，不绕过访问控制。

## 5. 失败与验证方法

来源失败、无发布时间、错误归并与建议缺乏依据是不同问题。来源健康度按实际尝试的榜单入口统计，报告是否足以支持本次选题另行判断。全部来源失败时程序返回非零状态；部分成功仍需展示失败来源。

本地测试验证解析、归并和调度等工程逻辑，无法证明当天来源可用。一次网络成功也不能外推长期健康度。实现见[工程说明](../src/daily-trend-radar/README.md)、[采集入口](../src/daily-trend-radar/scripts/run.mjs)和[来源配置](../src/daily-trend-radar/config/presets.json)。

## 6. 当前结论与下一步

已定位命令行未使用系统代理造成的超时，沿用代理后完成三源 15 条真实采集与三个选题简报；修复全源失败不保存报告的问题并通过回归，见[实际任务](../demo/daily-trend-radar/2026-10-16-source-check/README.md)。只验证本次三源，不推导全源长期可用率；现有样本未覆盖跨源同事件正例。工具仍独立，未自动接入其他工作流。
