# content-agent：在产品事实与账号规则内完成研究、写作和审改

本板块是独立 Python 工程，服务自有产品的内容生产。它把产品资料、账号表达和研究结果带入生成过程，并控制审稿、改稿、保存及发布处理。

以下是基于配置、程序和历史数据的产品复盘。本轮未找到可采用的相关创作聊天，不补造当时的动机、使用频率或用户反馈。依据见[背景记录](evidence-notes.md)。

## 1. 使用场景与问题定义

工程中的账号定位是独立产品创作者，产品资料涉及 ISS Tracker、BirdTracker、Math Puzzle、Soulnio。内容要解释产品适用的具体场景、功能和边界，面向可能使用产品的读者。

单篇生产需要选择产品和角度、研究相关表达、写作、校对产品事实、修改并保存。若每次只给模型一个产品名，存在遗漏功能边界、语气不一致、写成通用工具推荐或编造体验的风险。若把传播性作为唯一目标，又可能出现无法支持的承诺。

这些风险可从[账号定位](../src/content-agent/memory/account/persona.md)、[编辑规则](../src/content-agent/memory/account/editorial_rules.md)与[验收标准](../src/content-agent/memory/account/acceptance_standards.md)确认是系统明确约束的对象；文件中的历史观察和效果描述尚未独立核实。

## 2. 产品目标与完成条件

目标是生成可供本人审阅、修改和采用的产品草稿，并保留足够记录解释为什么生成、为什么修改或为什么失败。

| 优先级 | 要解决的事 | 首版验收条件 |
| --- | --- | --- |
| 必须 | 产品表达有依据 | 功能与边界能回查产品资料；不补造收入、下载量、评价或真实经历 |
| 必须 | 内容有具体用途 | 说明读者场景、实际功能、可执行动作与适用边界 |
| 必须 | 审改有终点 | 有明确检查与修改原因，达到条件或轮次上限后终止 |
| 必须 | 状态可解释 | 草稿保存、人工验收、发布结果分别记录 |
| 后续验证 | 研究值得投入 | 比较研究输入对具体性与人工修改的影响，同时计入采集和调用成本 |
| 后续验证 | 长期规则稳定 | 策略建议有样本依据，经人工确认后再更新账号记忆 |

模型评分只是流程中的判断信号。人工作用是决定是否采用；实际流量、点击或转化需要额外数据，不能由评分推出。

## 3. 两类任务与运行方式

```text
日常：产品与账号记忆 → 指定主题／自动选题
                      → 同题研究 → 初稿 → 检查、审稿、改稿
                      → 保存草稿 → 发布模块
长期：创作者和笔记样本 → 策略分析 → 建议 → 人工确认后更新记忆
```

单篇、按产品批量生成、长期策略研究有各自[入口](../src/content-agent/README.md)。程序读取本地 Markdown 记忆和 skills/ 提示词，模型推理调用在线 API；本地存放文件不等于离线推理，也不等于实现了宿主 Agent 平台。

[创作循环](../src/content-agent/src/create/runtime.py)执行结构校验、本地部分事实规则、模型审稿及有限改稿。默认最多五轮审稿，满足条件返回草稿和审稿记录，否则抛出错误。本地规则无法覆盖所有事实错误，模型评分也可能偏差。

研究的部分中间产物默认不长期保存，需要回溯时使用 --persist-research-artifacts。--no-publish 用于仅生成草稿；默认入口会尝试发布，--publish-dry-run 仍操作发布页。作品集演示先以草稿交付为范围。

## 4. 方案选择与代价

| 设计问题 | 当前方案 | 可比较方案与代价 |
| --- | --- | --- |
| 如何保持事实和账号一致 | 产品、账号、平台规则作为文件输入 | 每次临时描述更轻量，但容易遗漏；持久规则需要维护，过期资料会持续影响输出 |
| 如何提高内容具体性 | 先做选题和同题研究，再写作 | 直接生成调用更少；增加研究也引入样本偏差、采集失败和额外等待，收益需验证 |
| 如何安排质量检查 | 结构／规则检查与模型审稿结合，有限改稿 | 一次生成更快；无上限审改可能消耗失控，当前方案仍需人工最终判断 |
| 如何更新长期策略 | 单独研究并人工确认记忆更新 | 自动写回更省操作，但可能把一次样本偏好变成长期规则；人工确认增加维护成本 |
| 如何判断任务完成 | 分开记录生成与发布 | 一个总成功状态简单，却无法解释稿件可用但发布失败；分阶段状态更便于定位 |

这些比较为当前设计提供理由，尚未构成多种方案的实验排名。

## 5. 异常与质量处理

采集不足要说明样本条件，不能宣称充分研究。结构不合格、事实风险、模型请求失败和审稿未通过分别记录；审改达到上限后保留失败原因，不能靠更高模型自评分掩盖问题。发布失败与草稿验收分开处理，后续重试需要确认实际平台状态。

已有一份内部 approved 草稿、三天日志和发布失败文件，详见[历史材料](../demo/content-agent/README.md)。它们证明存在历史运行记录，尚不能证明完整任务成功率、人工采纳率或传播效果。

## 6. 当前结论与下一步

已按 run_id 对应历史审改、草稿和发布页准备失败，并依据产品资料完成一份候选稿的事实复核。作品集副本修复发布异常导致的保存计数失真，新增回归通过，见[复核与修复](../demo/content-agent/2026-10-16-draft-review/README.md)。当前未配置模型 API Key，未新增生产模型运行；评分阈值以 runtime.py 为准，不将模型评分当成人工采纳。


本轮继续检查时，发现 guard 失败后的改稿提示会建议把模型 API 与本地文件管理说明放进产品稿，偏离了目标读者。作品集副本改为要求围绕选定产品、使用其资料支持的能力，删除无依据主张，同时避免将内部实现和审校说明写进正文。验收文档的重复总分门槛同步统一为实际的 8.6。新增四项离线回归覆盖改稿提示、低分但模型判通过、事实阻断与轮次上限；它们验证控制行为，尚不能证明新提示提高了模型生成质量。
