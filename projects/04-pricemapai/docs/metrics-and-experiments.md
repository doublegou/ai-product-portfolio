# 用任务质量决定下一步投入

[返回项目](../README.md) · [需求规划](product-design.md) · [可复算结果](../evaluation/README.md)

## 核心价值与指标树

我希望产品帮助使用者完成一次**知情的候选核对**：知道自己需要什么规格，理解候选差异，并能回查对应原站。页面浏览与外链点击容易测量，却不能单独证明这件事发生。

| 层次 | 指标与口径 | 用来决定什么 |
| --- | --- | --- |
| 用户价值 | 观察任务中，正确说明关键条件并找到对应原站的完成比例；核对耗时、误解数 | 聚合入口是否比逐家查找更有价值 |
| 行为代理 | 同一会话内完成相关详情查看与原站跳转的比例；分别统计订阅与 API | 哪条路径容易中断，哪些候选值得维护 |
| 回访价值 | 首次完成核对的用户，在随后 7 / 30 天内再次完成相关任务的比例 | 是否形成重复需求；低频采购不只看 DAU |
| 数据质量 | 有效且有货覆盖、严格可比组覆盖、规格错配、商品链接身份正确率 | 能否扩大比较范围，是否应该先修数据 |
| AI 选型质量 | 单位 / 币种 / 分组倍率一致性；模型与监测范围是否清楚；复杂计费正确降级 | 页面是否帮助理解成本，而不是制造错误排序 |
| 运行效率 | 关注加权的新鲜覆盖、源站至公开页面的延迟、每千条有效报价更新成本 | 调度和发布投入是否值得 |

“有效且有货”按记录自身的有效期与库存判断；严格可比还要求规格明确且存在至少两家来源。两者不能相互替代。监测可用率来自商家披露，不能充当本产品独立的模型质量评测。

## 质量诊断决定优先级

我用 10 月 17 日的完整公开快照回放生产规则，先检查用户看到的信息是否足以支持决策。

| 诊断 | 结果 | 决策含义 |
| --- | --- | --- |
| 目录覆盖 | 50 个订阅类别，45 个有报价；360 个商家标识 | 已具备发现候选的广度，下一步优先改善理解与比较 |
| 有效数据 | 4,749 / 4,822 条订阅报价在采样时未过期，其中 2,873 条有货 | 98.49% 是当前 TTL 内比例，不能写成 98.49% 实时准确率 |
| 规格完整性 | 4,808 条标记待复核；6 条通过严格比较资格；多商家可比组为 0 | 规则保守与原始规格不全共同压低覆盖；需要标注样本定位原因 |
| 目录标签差异 | 41 个类别显示“最低价”，其中 39 个所选报价仍标记待复核 | 目录起价不应被理解为已完成同规格比价，列为 P0 表达与规则一致性问题 |
| API 成本语义 | 3,319 条报价中，2,416 条按 Token、620 条阶梯、280 条按次、3 条按图 | 多种收费模型无法用一个最低倍率完整表达 |
| 可计算综合系数 | 1,809 条报价满足现有综合系数计算条件 | 其余保留原条件；比例不是模型质量或价格准确率 |
| 公开数据完整性 | 19 页哈希一致，生产加载器接受完整数据；三种注入故障均拒绝 | 保证页面不会把残缺、混版或重复数据当成正常结果 |

**当前最值得投入的是让“找得到”变成“比得对”。** 我先统一目录起价与严格最低价的表达，再以高需求类别建立标注集，逐步提高规格覆盖。没有放宽资格规则来提高看起来好看的可比数量。

## 三个有明确决策出口的实验

以下是下一阶段实验协议；结果不与已经完成的快照回放混用。

### A. 规格与金额能否被正确理解

从充值、成品号、共享、月 / 年、体验期、地区限制和额度商品中分层选取真实样本；API 覆盖现金 / 额度、已含 / 未含倍率、Token / 固定 / 阶梯计费。第一批建议 120 条订阅与 60 条 API，作为人工标注工作量规划，**不是已执行样本数**。

对每条保存原站说明、SKU、时间和正确解释。开发样本与冻结验收样本分开，按商家切分，减少同模板泄漏。比较当前规则与候选规则的规格完整率、关键字段精确率、错误归组率、拒绝率，尤其单列充值 / 成品混淆、时长错配、币种及倍率错误。

放行条件：冻结集中不得新增关键金额或交付错配；覆盖提高时同时报告样本量和区间，不宣称总体零错误。标签语义不依赖模型升级，先消除目录“最低价”的歧义。

### B. 产品是否减少核对负担

采用订阅续费和 API 开发任务各一组，先以 6–8 位有实际需求的使用者做探索性任务观察。对照“逐家查找”和“聚合页面”，交叉安排顺序，使用不同但难度相近的目标，避免记忆影响。

记录候选找到时间、条件解释、原站对应商品、误解与放弃原因。重点看用户能否识别现金 / 额度、充值 / 成品、监测范围差异，而不是仅问是否喜欢页面。小样本用于发现问题；只有完成任务且误解不增加，才考虑更大样本验证效率差异。

### C. 关注度调度是否值得额外复杂度

将历史请求、采集结果、价格 / 库存变化与成本记录形成按时间前推的离线回放，分别运行固定周期和自适应策略。用相同时间窗、来源集合和请求预算比较关注加权的新鲜覆盖，并检查冷门来源最长等待、失败重试和缺货恢复。

先离线评估，再对来源分层开展有限线上试验；采集影响共享数据，不直接对访客做价格数据 A/B。只有相近预算下任务相关覆盖改善、冷门来源没有长期失去更新，才扩大自动调度范围。没有完整时序记录前，不将单个增量批次的体积变化写成月度成本收益。

## 活跃与留存怎样用才有意义

本产品偏任务驱动：用户可能在订阅到期或更换模型时才查一次。DAU / MAU 可以描述访问，但我会优先观察有需求用户是否完成核对，以及下一次需要时是否回来。

当前实现接入 Umami 与 GA4，包含详情、筛选、购买 / API 外链等事件。正式域名之外不发送交互事件，统计异常不阻断购买入口。来源 ID 采用域名与路径，避免把数据库 ID 或推荐查询参数用于身份字段。

[埋点实现](../src/pricemapai-web-production/src/lib/analytics.ts) · [历史事件联调](../src/pricemapai-web-production/deploy/umami/analytics-alignment.md)

会话漏斗需要用实际事件序列去重并校验来源；跨日留存需要稳定且合规的匿名用户口径，不能用调度使用的 24 小时聚合计数反推。当前案例尚无可核验的生产用户统计，因此不填 DAU、MAU、留存率或成交率。历史事件联调证明链路可接收事件，不代表真实用户增长。

## 商业化与规模化的前置条件

近期价值是可靠的信息查询。若开展渠道合作，商业关系须可识别，赞助位与自然比较分开，外链不等于成交归因；不得用合作权重影响价格排序。工作负载计算与更新提醒可作为后续需求，但要先证明规格正确、数据持续有用与任务重复发生。

规模扩大时，我会同时看每千条有效报价的采集 / 发布成本、任务相关覆盖和查询完成质量。模型调用成本目前为零是因为没有在线推理链路，不意味着数据采集、存储、同步或维护没有成本。
