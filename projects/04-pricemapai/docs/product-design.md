# 产品规划：用户定位、MVP 与持续运营

[返回项目](../README.md) · [技术方案](technical-design.md) · [指标与实验](metrics-and-experiments.md)

## 产品定义与切入点

**PriceMap AI 为选购 / 续订 AI 服务的个人用户，以及选择模型 API 渠道的开发者，提供从发现候选、解释价格到核对原站的信息比较工具。**

我优先选择已有明确目标的用户：个人知道想用哪个 AI 产品，开发者知道需要什么模型或能力。他们此时要解决的是渠道与条件选择，而不是学习 AI 是什么。第一阶段围绕“少跑几个站点、少误解一个条件、找到对应商品”形成可观察的价值假设。

| 定位选择 | 为什么这样选择 | 对范围的影响 |
| --- | --- | --- |
| 面向个人与独立开发者的轻量选购任务 | 可以围绕一次续费或模型接入观察完整过程 | 首版无需团队采购审批、合同管理或企业 SLA 承诺 |
| 同一产品内保留订阅、API 两条入口 | 都需要聚合来源与更新时间，但决策字段不同 | 共用采集 / 发布基础，分别设计筛选、详情与比较条件 |
| 先做信息比较，再评估交易或推荐 | 价格透明与条件理解是更靠前的任务 | 候选发现、解释与原站核对构成 MVP，交易履约暂不承接 |

产品价值目标是减少查价和理解条件的负担。只找到一个便宜数字并不意味着完成任务：使用者还要知道购买的是账号还是充值、期限是否匹配、API 的现金成本如何换算、数据何时确认过。

## 用户要完成的决定

| 用户与场景 | 想完成的任务 | 关键误判 | 当前产品响应 |
| --- | --- | --- | --- |
| 已有 AI 账号的个人用户 | 在预算内选择合适的续订渠道 | 成品账号被当成续费；体验期被当成整月 | 产品族、交付方式、原始标题、时长与原站入口 |
| 使用模型 API 的开发者 / 独立产品作者 | 找到值得进一步试用的渠道 | 余额单位被当成现金；最低倍率被当成模型统一折扣 | 模型与分组、输入 / 输出单位、币种与计费模式分开 |
| 回访查价者 | 判断之前的候选是否仍值得核对 | 旧价格、缺货或链接迁移仍被当成当前可用 | 采集时间、库存、过期提示、原站回查 |
| 产品维护者 | 用有限预算维持有用覆盖 | 失败重复消耗、冷门缺货来源持续高频、部分结果覆盖完整数据 | 队列、租约、试采集、失败保留、分档调度与预算 |

交易履约、账号安全与模型真实身份不由价格目录证明。当前产品不代收款、不保存用户 API Key，也不执行真实模型调用；外链后的交易与服务由原站承担。

## 我依据什么作出这些选择

现有依据包括历史演示、原站接入记录、购买路径修复、生产发布记录及可复算的公开快照。以下将其归纳为产品需求，而非补写不存在的用户访谈。

| 可观察问题 | 对产品的解释 | 已采取的行动 |
| --- | --- | --- |
| 同名订阅含充值、成品号、不同期限；标题出现额度、地区、首月等条件 | “名称相同”不足以建立价格比较对象 | 保留原始标题，设置比较键与复核状态；Codex 额度充值单独归类 |
| 一些 API 只有分组监测，另一些只给总吞吐 | 监测范围比数字本身更重要 | 标明实际探测模型、范围与时间；缺失不当零，不从延迟推算吞吐 |
| 价格接口可读，但购买地址错误 | 查询价值在原站核对环节断开 | 按商家路由修复，更新旧报价及静态快照 |
| 部分来源失败、空结果或只返回部分商品 | “没有拿到”不一定等于“已经下架” | 失败保留旧数据；仅完整结果处理消失项 |
| 访问量与采集 / 发布开销不必同步增长 | 可将前台读取和后台生产拆开 | 静态快照、增量同步、关注度驱动的采集调度 |

[购买链接案例](../src/pricemapai-web-production/docs/purchase-link-audit-2026-10-10.md) · [原站覆盖核验](../src/pricemapai-web-production/docs/merchant-coverage.md) · [公开快照回放](../evaluation/README.md)

后续用户研究首先验证任务是否成立：观察使用者用现有方法找到候选需要哪些步骤，再看聚合页面是否减少核对负担。购买意愿、信任来源、规格误解和放弃原因分别记录。

## 替代方案与选择

| 使用方式 | 有效之处 | 仍由用户承担的工作 | 我的取舍 |
| --- | --- | --- | --- |
| 直接逐家查原站 | 最接近商家当前说明 | 找来源、抄价格、统一规格、反复回访 | 保留为最终核对与任务对照基线 |
| 社群推荐或静态价格表 | 发现候选快，解释可集中 | 时效、来源范围和可比口径不固定 | 用原站来源与采集时间补足可追查性 |
| 价格聚合目录 | 集中发现候选与筛选 | 需要继续核对库存、规格、来源与交付 | 当前产品形态，优先完成查询质量 |
| 自动代理购买或智能推荐 | 能减少决策动作 | 需要偏好、可信质量数据、交易和错误承担机制 | 暂不进入 MVP，先让推荐依据成立 |

项目曾参考 PriceAI 的类别与交互事件，并使用自有原站采集链路；我没有将参考目录的报价或监测作为自采结果。第三方素材的声明保留在源码中。

## MVP：把一条查价任务做完整

**价值假设：**集中候选、明确条件、保留原站核对入口，可以降低重复查找和解释负担，同时避免不同规格被误当成同一商品。

| 范围 | 首个闭环必须交付 | 当前状态 |
| --- | --- | --- |
| 找到候选 | 订阅 / API 分入口，类别、搜索与详情 | 已实现，有历史演示 |
| 理解条件 | 标题、交付、时长、库存；模型、分组、单位、币种 | 已实现；部分规格仍需人工核对 |
| 判断时效 | 采集确认时间、过期状态、加载失败提示 | 已实现；公开延迟包含批次与缓存 |
| 核对原站 | 可访问的对应商品或模型报价页 | 已实现并修复过错误路径；不保证外站永久可达 |
| 持续维护 | 试采集、暂停、日志、事务写入与失败恢复 | 已实现，管理能力与公开阅读分离 |
| 效果判断 | 任务观察、有效比较覆盖、原站核对动作 | 埋点和快照诊断已有，完整任务研究待执行 |

首个价值时刻是使用者能解释为何选择某个候选，并回到对应原站确认条件。仅打开目录、看到最低数字或点出外链，都不是这一价值的完整证明。

## 迭代脉络：范围随实际问题变化

| 阶段 | 具体问题 | 交付与取舍 |
| --- | --- | --- |
| 初始产品与数据接入 · 10 月 9 日 | 两类采购任务需要统一入口与真实报价 | 前端、原站适配、数据库、管理页和生产部署；补 API 中转站路径 |
| 公开交付 · 10 月 9–10 日 | 前台访问直接读取后端，规模增长牵动数据库开销 | 转为独立静态快照服务；完整版本原子切换，关闭旧公开查询 API |
| 需求与变化驱动 · 10 月 10 日 | 统一频率浪费采集预算，热点和缺货来源价值不同 | 关注度、价格 / 库存变化、缺货观察、独立热点核验 |
| 旅程修复 · 10 月 10–11 日 | 分类、跳转、库存与中文输入影响实际使用 | 额度分类、详情定位、SKU 库存、购买路由、中文 IME 修复 |
| 发布效率 · 10 月 12 日 | API 报价数组变化造成大批替换，监测频繁变化增加流量 | 稳定 ID 增量、监测单独节奏、30 分钟发布批次与 45 分钟热点有效期 |

这些是已提交的工程演进。以下需求池是基于现有运行结果作出的下一阶段规划，不与历史版本混用。

## 需求池与当前顺序

排序先看错误决策和任务阻断，再看可验证收益、数据依赖与维护成本。

| ID / 优先级 | 需求 | 当前状态与下一步 | 验收方式 |
| --- | --- | --- | --- |
| R01 / P0 | 目录起价与同规格最低价使用一致表达 | 当前两套规则不同；先统一标签与说明，再扩展自动比较 | 所有“同规格最低”都能回查资格、币种、期限、交付与至少两家来源 |
| R02 / P0 | 提升规格完整性 | 标题规则已有，严格可比覆盖低；优先常用类别与高关注商家 | 独立真实样本对照 SKU / 原站说明，覆盖和错配同时报告 |
| R03 / P0 | 原站链接持续正确 | 已修复多类路径；建立按商家、路由与变化分层的抽查 | 对应商品身份正确，外壳页 / 迁移 / 防护分别处理 |
| R04 / P1 | 区分更新慢与已经失效 | 原时间与过期状态已有；补来源年龄分布与端到端延迟观察 | 不用页面刷新时间覆盖来源时间；停更时正确降级 |
| R05 / P1 | 验证自适应调度的实际收益 | 调度已实现；固定策略对照尚未完成 | 相近资源预算下，关注加权的新鲜覆盖提升，低需求来源不饥饿 |
| R06 / P1 | 观察首次与再次查价 | 事件已接入，任务级理解和满意数据缺失 | 用户能识别规格 / 币种 / 监测边界，第二次有需求时自主回访 |
| R07 / 条件进入 | 按实际工作负载估算 API 成本 | 已有单位化报价；工作负载计算器未实现 | 输入 / 输出、缓存、阶梯与固定费分别计算，条件缺失时不输出伪精确总价 |
| R08 / 条件进入 | LLM 辅助规格归一 | 当前无生成模型参与线上判断 | 只产结构化候选与证据，金额和单位用确定性规则校验；不自动发布未核实结论 |

当前不扩展交易、模型代理路由、商家信誉评分或无依据的推荐榜。它们需要额外的履约、质量和偏好证据，不能从现有报价覆盖推导。

## 获客、激活与回访：围绕选购需求组织

产品已经有宣传演示、公开查询入口和交互埋点。下一阶段的运营设计围绕具体任务展开，不把曝光与访问直接当成产品价值。

| 环节 | 产品 / 运营设计 | 验证问题 |
| --- | --- | --- |
| 发现产品 | 用订阅续费与 API 成本解释内容展示使用场景；入口指向相关类别而非泛首页 | 哪种任务带来有相关需求的访问？不以所有访问混算渠道效果 |
| 首次激活 | 无需注册即可查报价，快速进入类别 / 模型详情，保留原站核对入口 | 是否找到目标候选、理解关键条件并完成原站核对？ |
| 再次使用 | 现阶段依靠持续更新的目录与直接回访；收藏、变价提醒为待验证方向 | 用户下一次有续费 / 接入需求时是否回来，缺什么才需要提醒能力？ |
| 转化与收入 | 先验证可理解、可核对的候选是否产生持续需求，再评估合作与增值 | 外链意图、成交归因与收入分别统计；合作不能影响自然排序 |

潜在优势来自持续维护的规格映射、原站适配和错误修复积累，但其是否构成稳定留存优势仍需验证。短期不以新增来源数量代替这些工作，也不提前把展示流量写成商业模式成立。

## 从成立到复用，再到规模

**0→1：**查询、原站数据和持续发布已经上线，双路径有实际演示。当前关键问题是把“能找到信息”进一步验证为“能正确理解并完成核对”。

**1→10：**先改善规格和链接质量，用完整查价任务观察理解错误、核对耗时与再次使用。稳定数据质量后，再扩展主要类别的来源覆盖。

**10→100：**在任务复用成立、单位更新成本可控之后，评估工作负载计算、订阅提醒或研究数据服务。渠道合作的收益归因与自然排序分开，商业化不能破坏比较依据。[指标与实验](metrics-and-experiments.md)
