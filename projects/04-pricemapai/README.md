# PriceMap AI · AI 订阅与 API 渠道比较

**让使用者看懂价格背后的规格、时效和来源，再决定去哪里核对与购买。**

我独立推进 PriceMap AI 的产品设计、数据接入、工程整合与上线迭代。它服务两类决策：个人选择 AI 订阅渠道，开发者比较 API 模型报价与公开服务信息。产品在同一入口组织分散信息，保留原始标题、原站链接和更新时间，帮助使用者缩小核对范围。

## 从使用需求到最小产品闭环

用户面对的困难不是没有价格，而是**价格对应的东西可能不同**：成品账号、充值与共享账号混在一起，期限不同；API 则同时存在输入 / 输出价格、分组倍率、充值额度、按次与阶梯计费。把数字直接排序，会把解释成本重新留给用户。

我把 MVP 定义为：**找到目标产品 → 看懂候选条件 → 判断数据是否仍有效 → 到原站核对**。第一阶段保留规格、库存、来源和错误状态；账户体系、交易闭环、自动推荐和独立付费探测暂不进入范围。

| 用户任务 | 最小交付 | 为什么这样取舍 |
| --- | --- | --- |
| 为已有账号续订 | 区分充值与成品号，展示时长、原始商品说明和库存 | 避免低价但交付方式不同的商品造成误判 |
| 为开发任务寻找 API 渠道 | 保留模型、分组、单位、币种、监测范围与来源 | 倍率不是普遍折扣，可用率也不等于模型质量 |
| 维护不断变化的报价 | 能试采集、暂停来源、查看失败并保留旧结果 | 原站变化是日常状态，需要恢复路径而非一次性抓取 |

需求依据来自实际使用演示、原站接入与修复记录；用户分层是对这些任务的产品归纳，未将其写成已经完成的访谈研究。[研究依据、替代方案和需求池](docs/product-design.md)

## 架构：把数据可信度和运行成本放进同一条链路

![PriceMap AI 的用户路径、数据生产与公开交付架构](demo/assets/architecture.svg)

**React / Vite → Cloudflare 静态资产；Supabase 承担采集与唯一报价数据库；独立同步 Worker、Durable Object 和私有 R2 处理增量发布。** 访客读取静态 JSON，不因一次页面访问触发商家采集、数据库查询或模型调用。

| 产品约束 | 工程方案 | 接受的代价 |
| --- | --- | --- |
| 数据量扩大不能让每次访问都打数据库 | 版本化、gzip 分页、完整读取后切换；旧版失败时仍可用 | 数据可见时间包含采集、批次发布和缓存，不能承诺实时 |
| 相同商品容易因标题、币种或单位错配 | 标准类别、严格比较键、API 单位与币种归一；缺失信息留待确认 | 自动可比覆盖低于目录覆盖，需要继续治理规格 |
| 原站不稳定且预算有限 | 到期队列、租约、失败退避、按关注 / 变化 / 缺货分档 | 热门来源优先；低需求或持续缺货来源更新更慢 |
| 一次失败不能抹掉已有结果 | 事务写入、完整快照才处理消失商品、增量幂等与版本断档恢复 | 保留旧数据时必须同时保留原时间与过期状态 |

## 三个关键判断

### 1. 先区分“可以展示”与“可以比较”

API 数据将人民币、美元和美元计价额度分开。原价已包含分组倍率时不再相乘；阶梯表达式不强行转成一个单价；每张、每次、每秒分别保留。用户需要核对相同模型和工作负载，站点最低综合系数只能作为线索。

订阅详情的同规格最低价要求明确比较键、无需复核、有货、有效，并且至少有两家不同来源。目录则使用更宽的类别起价，两者目前尚未完全统一。真实快照回放显示：4,822 条报价中，2,873 条在采样时有效且有货，但仅 6 条通过严格资格筛选，未形成多商家可比组。

**因此下一版优先改善规格识别和目录表达，而不是放松规则来制造更多“最低价”。** 这组结果衡量当前规则覆盖，不是商品真实性或分类准确率。[原始数据、口径差异与下一轮验证](docs/metrics-and-experiments.md#质量诊断决定优先级)

### 2. 价格正确，还必须把人带到正确商品

曾有采集器能取得报价，却生成了错误购买路径。我将“数据抓取成功”与“商品链接正确”拆开验收：商品编号、标题和路径对应，完整目录中的消失商品才停用；通用网页外壳不能凭 HTTP 200 判通过。

修复覆盖配置、历史报价和公开快照，避免只改新采集而留下旧数据。这个案例把用户旅程的最后一步纳入了工程交付，而非停在列表可显示。

### 3. 把更新预算用于值得更新的数据

最初统一频率采集；后续根据去重访问兴趣、价格 / 库存变化和缺货状态调档。购买意图比普通浏览具有更高调度权重，手动配置保持优先；这些权重影响后台采集，**不改变前台自然价格排序**。

公开发布进一步从全量传输演进到按稳定报价 ID 的增量。当前代码将价格与新鲜度按 30 分钟批次同步，监测字段按 2 小时更新；预算耗尽时保留未确认批次和旧版公开数据。当前快照的 19 个压缩分页合计约 0.74 MB，解压约 8.68 MB；这是文件体积，不是页面测速或整月费用节省。

[版本演进与资源取舍](docs/technical-design.md#从统一采集到按价值分配预算)

## 下一阶段怎样判断值得继续投入

我的核心价值目标是**使用者完成一次知情的候选核对**。已有埋点覆盖详情、筛选和原站外链，可作为行为代理；需要结合任务观察，确认用户是否理解规格差异、找到合适候选，而不把点击直接写成满意或成交。

| 优先顺序 | 下一项验证 | 进入下一阶段的条件 |
| --- | --- | --- |
| 质量收敛 | 统一类别起价与严格比较表达；建立真实标题、SKU、时长和计费标注集 | 关键规格错配被阻断，覆盖提升有独立样本支持 |
| 稳定复用 | 分时段检查有效数据、购买地址与发布延迟；观察完整查价任务 | 结果可核对，错误和等待没有抵消信息聚合价值 |
| 持续运营 | 比较关注加权的新鲜度与采集 / 发布成本 | 更新策略改善任务相关覆盖，再扩展来源和商业模式 |
