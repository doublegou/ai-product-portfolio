# 产品决策：从个人记录任务到端侧 AI 产品

[返回项目](../README.md) · [原始需求与 MVP](product-discovery.md)

我围绕“录完后能理解、能核对、能继续用”设计 StayWord。产品形态、AI 路线、交付状态与版本范围相互约束，下面结合[版本演进](product-discovery.md)复盘这些选择。

## 为什么做个人记录工具

用户从一段谈话出发，首先需要快速了解内容、找到原话和带走资料。我让原音频、转写、摘要和编辑归属于同一条记录，减少在播放器、文本和笔记工具之间重新关联内容的工作。

| 产品选择 | 放入当前范围的价值 | 同时接受的代价 |
| --- | --- | --- |
| 个人记录优先 | 录制或导入即可开始，围绕一段谈话完成任务 | 暂不提供团队账号、协同编辑和行动项分配 |
| 原生移动入口 | 录音、文件导入、锁屏播放与系统分享贴近已有操作 | 需要分别处理 iOS 与 Android 的运行和后台限制 |
| 本地核心处理 | 核心谈话材料留在设备，减少网络和云服务依赖 | 模型体积、等待和兼容性由设备承担 |
| 一次购买 | 使用成本不随录音时长增加，符合个人工具定位 | 持续模型适配与支持必须纳入维护预算 |

摘要在这里是帮助概览的一层能力。重要日期、责任归属和原话措辞仍需要回查，因此时间戳、编辑与原音频保留从一开始就属于产品核心。公开同类工具的功能比较见[定位分析](public-positioning.md)。

## 端侧处理：减少服务依赖，也承担设备成本

云端可以使用更大模型、集中更新推理服务；端侧则减少录音上传和网络依赖，但让模型加载、内存、安装体积和兼容性影响每一次体验。我采用端侧方案，并用量化模型、串行任务和可保留的中间结果控制资源压力。

端侧路线减少了按转写时长增长的应用服务端推理开销，但版本升级仍需要投入。关键是用户获得的长期价值能否覆盖持续适配与支持，而不仅是一次请求的 API 费用。

| 成本或约束 | 产品上的响应 | 何时需要重新判断 |
| --- | --- | --- |
| 模型随包分发、安装占用 | 将核心模型与应用交付，运行要求中明确依赖 | 安装与更新成为实际获取障碍时，评估按需分发及离线准备流程 |
| 低内存、GPU 能力差异 | 量化、串行、平台分别配置运行与降级策略 | 目标设备无法可靠完成任务时，收窄支持范围或换模型 |
| 后台限制 | 保存已有资料，明确暂停与恢复行为 | 真实用户频繁离开应用且无法等待时，重评长任务设计 |
| 持续模型适配和用户支持 | 将适配、回归与支持纳入版本成本 | 新增用户收益无法覆盖持续负担时，重评定价与范围 |

两端共享用户任务，运行策略分别实现。iOS 收敛到随包模型，Android 根据系统能力尝试生成、本地模型与抽取；我以结果类型和恢复成本管理差异，而非要求底层实现完全相同。[双端架构](technical-design.md)

## 倍速与分享：把生成结果变成用户可以使用的材料

用户反馈提出了倍速与三类分享，我将它们纳入 1.0.2。它们改善已有任务的核对和交付环节，比引入新的生成入口更直接。

这里的验收对象是用户动作：倍速后能否继续定位原话、分享是否拿到正确内容、取消分享是否影响原文件。实现因此包括速率持久化与系统播放同步、导出资料快照、空内容判断、临时目录和清理，而非只增加两个按钮。[实现细节](technical-design.md)

我没有在这一版扩展 iOS 16，手表录音也留到后续评估。重新考虑它们时，需要回答不同问题：前者需要知道被阻断的用户和适配代价，后者需要确认手机无法覆盖的记录场景。当前没有这些证据，不能只靠一条反馈就承诺新平台。

对于需求池里曾判断为技术上无法解决的“收音问题”，我重新按四层拆解：采集、语音检测、识别和摘要。先听原始声音是否清楚，再查漏段和错词，最后判断摘要是否改变含义。未录到的信息无法靠换摘要模型补回；距离提示、设备摆放或采集设置是否有帮助仍可验证。[需求池与重开条件](product-discovery.md)

## 发行与反馈：让产品承诺接上实际使用

官网、商店说明和介绍视频承担使用前的预期管理：让用户理解本地处理、系统要求、可得到的材料，以及哪些能力需要设备资源。实机演示按导入、处理、核验、分享和收藏展开，展示一次完整任务。

制作 StayWord 介绍素材时，我已有实机演示，因此只调用内容工作流生成文案与封面，再手动修改表达。这是从产品开发到发行准备的实际衔接；素材产出本身不等于已证明获客提升。[当期制作记录](../../01-content-agent/demo/script-workflow/2026-09-25-partial-task/README.md) · [产品官网](../src/official-landingpage/products/stayword/index.html)

应用内的设置提供语言、联系和评分入口。评分请求在本地满足使用天数与完成记录条件后触发，减少在首次价值出现前打断用户；这仍是交互规则，后续应通过首次任务完成与反馈验证效果。收集到的倍速、导出和设备诉求进入需求池，再结合质量与维护成本决定下一版范围。

## 摘要失败：已有成果与生成状态分别交付

| 情况 | 当前交付策略 | 必须区分的结果 |
| --- | --- | --- |
| ASR 完成，iOS 摘要失败 | 保留转写，单独保存摘要错误 | 转写可用，但摘要未完成 |
| Android 生成失败、抽取可用 | 保存抽取类型与抽取结果 | 降级产物可读，不等于生成摘要成功 |
| 中断后恢复 | 保留原音频与已保存结果；按平台恢复 | 能恢复与恢复时不用重复计算是两种保证 |

这些策略处理的是执行失败，**不能自动识别“顺利生成但内容错误”**。近期 AI 辅助离线诊断发现事实误写，而新增约束的提示词仍发生退化；这版候选没有合入。这使下一轮优先级从“完善输出格式”转向事实保留、语言控制与重复终止。[对照评测与否决依据](../evaluation/summary-probe/README.md)

## 从端到端错误定位投入方向

我把质量问题放回整条记录链路判断。输入不完整、识别错误、摘要误写与用户找不到结果，会表现为同一种“笔记不好用”，但需要不同改进。

| 问题发生的位置 | 如何诊断 | 产品改进方向 |
| --- | --- | --- |
| 采集与导入 | 原音频是否清晰、完整、可播放 | 录音提示、输入检查与资料保护 |
| 语音检测与转写 | 对齐音频与转写，查漏段、错词和时间戳 | VAD / ASR 配置与分段策略 |
| 摘要生成 | 给定正确转写，检查数值、否定与归属 | 模型、提示词或长文整合策略 |
| 结果使用 | 用户能否找到原话、编辑并导出所需材料 | 回听、编辑、分享入口与状态表达 |

这也是近期文本级诊断的用途：先隔离摘要层，避免把 ASR 错误和 LLM 错误混在同一个指标里。诊断之外仍需音频与真机验证，覆盖上游误差、长任务和资源约束。

## 后续改进怎样获得发布资格

候选改动使用同设备、同输入和固定标注对照，每次改变一个因素；先检查数字、否定、责任归属等关键事实，再比较耗时与内存。音频丢失、无提示假成功或关键事实反转应阻断候选发布。用户任务最终以找到正确信息和复用材料验收，模型格式通过仅是其中一环。[完整验证设计](../evaluation/README.md)
