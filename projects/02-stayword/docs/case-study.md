# StayWord：让本地 AI 的结果可以继续使用

[返回项目](../README.md)

## 产品问题与范围

录音之后的成本发生在回听、查找和整理。转写可以改善查找，但长文本仍然难读；只有摘要又容易丢失上下文。StayWord 把原音频、时间戳转写、摘要和资料管理放在同一条记录里，让阅读与核验可以来回切换。

以现有演示支持的任务作为主线：个人用户导入一段谈话，理解重点、回听原话、整理并复用内容。这是基于现有实现与素材的产品复盘，不补造访谈人数、历史调研或采用率。其他会议、访谈、课程场景需要分别验证，尤其不能把清晰短音频的表现推广到多人噪声长录音。

## 成功的定义

一次任务的成功应包含：音频安全保存；产生可阅读的转写或明确的失败提示；用户能核对并带走需要的内容。摘要是额外的信息组织层，不应覆盖转写与原音频的可用状态。

后续建议以“完成核验并保存或导出一条有效笔记的任务比例”作为核心体验指标。它比生成次数更接近价值，但需要知情的本地测试记录，当前没有这一线上测量。辅助指标分别看转写 CER/WER、摘要事实错误、关键事实覆盖、等待耗时、中断后的重复处理与数据丢失。

## 三项关键决策

### 端侧优先：以隐私和离线可用交换资源成本

云端方案可以降低模型随包体积，并灵活使用大模型，但增加上传、网络与服务依赖。当前产品采用本地转写和摘要，更适合不希望上传谈话的个人任务。这一选择要求控制内存、模型加载和后台行为，而不是只在文案上写“隐私”。

iOS 的 MLX 摘要依赖真机 GPU；Android 系统模型可用性不一致，因此使用系统能力、本地小模型和抽取结果三级策略。不同运行时对应不同平台条件，不能把相同品牌名称理解为相同能力保证。

### 结果可以追溯：摘要与原话保持联系

摘要便于概览，时间戳便于定位，原音频用于核验语义和识别错误。演示中的回听与摘要切换体现了这个闭环。当前没有逐条摘要到原文的引用映射，因此还不是“每个结论都有证据链接”的产品；应优先验证数字、人名和行动项归属，再评估句级来源定位。

长文本分块总结再整合，缓解一次输入过长的问题，但可能丢失跨段因果、在整合时再次压缩信息。验收应特意加入“前段提出、后段否定”和跨段同名人物等样本，不能只检查输出格式。

### 失败不抹掉已完成工作

iOS 将摘要失败单独记录；转写结束后即使摘要不可用，仍保留转写。后台中断可以利用持久化片段续跑。Android 避免因删除一条记录而取消整条任务链，生成失败时交付有类型标识的抽取摘要。

恢复不是一句“支持重试”：iOS 有采样位置检查点；Android 当前工作节点重新进入音频准备和转写，仍可能重复计算。可恢复与高效恢复需要分开验收。

## 发布与证据如何理解

历史演示证明特定版本完成了一条任务；App Store 查询证明发行页面存在；代码说明当前工程实现。三者不能相互替代。9 个评分不足以判断产品市场匹配；视频的速度说法没有配套基准日志，不作为作品集性能成绩。

## 下一轮优先级

| 优先级 | 工作 | 决策依据与验收 |
| --- | --- | --- |
| P0 | 固定音频集，人工标注转写与关键事实 | 建立数字、否定、人物归属错误基线，再决定模型或提示词改动 |
| P0 | 两端真机后台、终止、低内存和模型失败测试 | 先确认无音频丢失、无永久卡住、无静默假成功，再扩设备 |
| P1 | 生成、抽取、不可用三种摘要状态的理解测试 | 用户能识别当前产物的能力边界，而不是只看到“已完成” |
| P1 | 长录音分块一致性、耗时与峰值内存 | 质量和设备表现一起决定分块、调度参数 |
| P2 | 摘要句级来源、检索与云同步评估 | 基础记录可靠且有实际需求证据后扩展 |

发布候选至少应做到：测试集中无原音频丢失；中断不悄悄报告成功；关键数字和行动归属错误得到处理或明确提示。质量阈值在标注基线后预先冻结，不能看完结果再降低门槛。具体测试卡见[验证设计](../evaluation/README.md)。
