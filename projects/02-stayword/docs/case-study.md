# StayWord：把端侧 AI 做成可持续使用的产品

[返回项目](../README.md) · [用户研究与需求池](product-discovery.md) · [经营指标](metrics-and-experiments.md)

## 定位与替代方案

录音解决“记下来”，转写解决“能读”，摘要解决“快速理解”；用户最终要做的是从谈话里找到可信信息，并继续使用它。StayWord 将三类产物保留在同一条记录中，以回听、编辑、分享和资料管理闭合任务。

下表是方案级比较，不宣称做过竞品实测或覆盖市场全部产品。

| 方案 | 适合的任务 | 为何仍有 StayWord 的空间 |
| --- | --- | --- |
| 录音后人工回听 | 短录音、需要完整语气和上下文 | 长材料定位成本高；转写与概述可缩短查找路径，但需要实测正确率与耗时 |
| 将音频交给云端 AI | 接受上传、网络稳定、需要更大模型能力 | 本地处理提供不同的隐私和离线条件；代价是设备性能和模型能力受限 |
| 只保存转写或摘要 | 主要阅读，不再核对原话 | 识别、数字和归属错误难以确认；同一条记录保留原音频与时间戳更便于核验 |
| StayWord 本地流程 | 希望在手机内记录、理解、核验和复用 | 需要证明真实设备上的质量、恢复与等待体验，不能仅靠“离线”形成优势 |

## 决策一：端侧路线与买断模式要一起成立

公开官网采用一次购买、无持续订阅的定位。端侧计算减少逐任务云端推理支出，与此模式相容，但没有消除成本：模型与原生库分发、设备适配、版本回归和用户支持仍持续发生。[现有官网](../src/official-landingpage/products/stayword/index.html)

产品约束因此转化为四个工程问题：较小模型能否保留关键事实；长输入如何分块；手机内存不足如何交付部分结果；后台中断如何保住工作。现有方案采用本地 ASR、量化摘要模型和串行重型任务。iOS 与 Android 的运行时、系统限制不同，恢复与降级策略不能只复制同一张技术清单。

商业评估应分别记录 `净收益 − 可归属分发 / 服务 / 支持成本` 与一次性研发投入。现有 $17 proceeds 缺少完整窗口、成本和付费设备分母，不能推算毛利、ARPU 或 LTV。是否长期采用买断，需要后续支持负担和复购 / 新增结构共同判断。

## 决策二：投入核验和导出，而不只增加生成能力

倍速和三类分享来自真实 VOC。倍速缩短回听路径，导出让用户把音频、逐字材料和概述带到不同场景。两者利用已有资料，直接改善结果的使用阶段。

更新后的原始工程已经实现六档速率、偏好持久化和锁屏速率同步；导出对资料建立快照，生成独立临时目录，将转写按时间排序，保留音频扩展名，并在完成或失败后清理。这里的产品验收不仅是“按钮出现”，还包括分享取消是否安全、摘要为空能否被阻止、原音频是否保持完整。[实现与验收记录](../evaluation/README.md)

摘要仍是需要核验的信息组织层。当前没有逐条摘要到原文的引用映射，因此不能把可回听写成“每个结论都有来源引用”。下一步先用找事实任务验证用户是否能发现数字与归属错误，再判断句级来源定位的收益。

## 决策三：把模型失败定义成不同的产品状态

| 实际情况 | 应如何交付 | 不能怎样计数 |
| --- | --- | --- |
| ASR 完成，摘要失败 | iOS 保留转写，单独展示摘要错误 | 不把整条记录算丢失，也不算摘要成功 |
| 生成失败，抽取可用 | Android 保存抽取类型，让用户知道能力变化 | 不能混入生成摘要成功率，掩盖模型失效 |
| 切后台或任务中断 | 保留原音频和已保存结果，明确等待或恢复 | 不能用“可重试”掩盖重复计算和永久等待 |
| 输入收音不清 | 先定位采集问题，再判断识别与摘要错误 | 不能只归因于 LLM，也不承诺恢复不存在的信息 |

这使质量验收沿链路展开：采集 → VAD → ASR → 分块 → 摘要 → 核验 / 复用。每层各有失败类型，最终产品指标不能只看模型返回了非空文本。

## 一次已经执行的质量决策

本次对随包摘要模型完成 48 次离线推理，比较原始提示词与更严格的约束候选。候选在部分发现样本改善，却在额外样本和另一种子下产生禁止动作反转、无依据扩写与循环重复，因而没有合入产品。这个决定说明发布依据应是行为证据，而不是提示词长度。[实测与逐例判断](../evaluation/summary-probe/README.md)

## 如何决定模型与版本是否可以发布

当前使用的模型是工程事实，不把它包装为经过完整多模型 benchmark 后的“最优解”。下一轮对比需要控制变量：同一设备、同一输入、同一预处理，在当前配置与单一候选变更之间比较；先冻结人工逐字稿和关键事实，再运行推理。

| 决策维度 | 最小比较 | 如何影响发布 |
| --- | --- | --- |
| ASR | 原音频 + 人工逐字稿，区分漏语音与错词；中文 CER / 英文 WER | 发现 VAD 漏段先改采集 / 分段，不能只换摘要模型 |
| 摘要 | 人工正确转写输入与 ASR 转写输入分别运行 | 区分上游错误传播与摘要本身幻觉 |
| 分块 | 短输入、长输入、跨段否定与同名人物 | 查看整合是否保留后文修正，不能只测格式合法 |
| 性能 | 同设备冷 / 热启动，阶段耗时、峰值内存、降级比例 | 质量相当才比较速度；一次 OOM 不能被平均耗时掩盖 |
| 可靠性 | 后台、终止、缺模型、空间不足、取消导出 | 音频丢失、无提示假成功为发布阻断问题 |
| 人工使用 | 找到事实的正确率、耗时与修改成本 | 模型指标改善但用户任务变差时，不直接上线 |

最小诊断集为 6 类各 2 条音频，设计与记录模板见[验证方案](../evaluation/README.md)。这不是统计代表性样本。质量阈值应在建立基线后、评估候选前冻结；测试中发现重大事实错误时先归因修复，不用测试后调阈值“通过”。

## 当前判断与迭代顺序

真实材料支持：产品已发行，用户提出过具体需求，核心交付已演示，更新后的实现可检查，已有早期下载与收益。仍需回答的是“哪些人持续需要它”“AI 是否让正确找信息更省事”“哪些设备和输入会失败”。

先验证首次任务与收音 / 事实质量，再验证重复使用和设备成本，之后才决定扩渠道、旧系统或手表端。详细实验、统计口径与需求重开条件分别放在[指标与实验](metrics-and-experiments.md)和[需求池](product-discovery.md)，避免把计划写成已发生的业务成果。
