# 作品集与 AI 产品设计参考

检索与阅读日期：2026-10-17。下面记录实际借鉴的组织方式；外部作者自述的业绩不是 StayWord 的数据，也未在此独立审计。

| 参考 | 采用方式 | 在本项目中的落点 |
| --- | --- | --- |
| [Haris Rehman：AIPM 作品集拆解](https://www.harisrehman.tech/blog/ai-product-manager-portfolio)及其 [ChatlyAI 案例](https://www.harisrehman.tech/projects/chatly) | 先交代问题、约束、决策和结果；让指标有可解释来源 | 首页先呈现产品、已观察结果和关键取舍，数据口径单列 |
| [Product People：MVP 案例](https://www.getproductpeople.com/case-studies/crafting-an-mvp-from-scratch-as-interim-product-managers) | 将研究发现连到 MVP 边界、功能验收与后续验证 | VOC → 任务 → MVP → 需求池；不照搬多人团队流程 |
| [Varun Khanduja：研究优先级案例](https://varunkhanduja.com/case-study-prioritization) | 让优先级取舍可见，避免过度复杂的评分 | 区分做、不做、延期与重新诊断；缺少人数工时就不伪造 RICE 分数 |
| [Priyanka Shetty：Applied AI 产品案例](https://prishetty.com/case-studies/ai-pit-stop-applied-ai) | 将评估和发布条件放进产品闭环 | 同时讨论质量、延迟、成本、人工核验和降级结果 |
| [Google PAIR：用户需求与成功定义](https://pair.withgoogle.com/guidebook-v2/chapter/user-needs/) | 从用户任务选择 AI 价值与成功标准 | 比较正确找信息的耗时，而不是生成次数 |
| [Google PAIR：错误与恢复](https://pair.withgoogle.com/chapter/errors-failing/) | 将 AI 错误、使用情境与可恢复路径一起设计 | 分离 ASR、生成摘要、抽取降级和采集质量问题 |
| [Apple 指标定义](https://developer.apple.com/help/app-store-connect-analytics/reference/metrics-definitions)与[使用分析](https://developer.apple.com/app-store-connect/analytics/) | 保持商店、使用、收入指标的分母与样本口径 | 72 下载不改写为 72 活跃用户；日均转化不重算为产品页转化 |

判断本案例是否完整，应看读者能否沿具体证据理解一项产品决策，而不是是否出现了所有 PM 术语。尚未开展的访谈、线上埋点和 AI 基准均明确标注为计划。
